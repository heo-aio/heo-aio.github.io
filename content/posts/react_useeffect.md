## ⚡ useEffect 기본 - 렌더링 이후에 실행되는 코드

```jsx
import {useEffect, useState} from "react";

export default function Comp({cnt}){
    const [num, setNum] = useState(cnt);

    useEffect(function (){
        console.log(`num state 변경시에만 실행`);
    }, [num]);

    const incNum = () => { setNum(num + 1); }
    const decNum = () => { setNum(num - 1); }

    return(
        <div>
            <h1>Counter : {num}</h1>
            <button onClick={incNum}> + </button>
            <button onClick={decNum}> - </button>
        </div>
    );
}
```

`useEffect(함수, 배열)` 형태로 쓰고, 컴포넌트가 렌더링된 **이후에** 그 함수를 실행시켜준다. "렌더링 도중이 아니라 렌더링이 끝난 이후"라는 게 포인트인데, 왜 그런지 생각해보니 useEffect는 대부분 화면을 그리는 것과는 별개인 일(로그 남기기, 서버에 데이터 요청, 타이머 설정 등)을 처리하는 용도라서, 화면이 다 그려지고 나서 실행돼야 자연스럽기 때문이었다.

여기서 핵심은 **두 번째 인자인 배열(의존성 배열, dependency array)**이 "언제 실행할지"를 결정한다는 것이다.

> ✅ **핵심**: `useEffect`는 렌더링이 끝난 뒤 실행되는 "부수 효과(side effect)" 처리용 hook이다. 언제 실행될지는 두 번째 인자인 의존성 배열이 결정한다.

## 🔀 의존성 배열 3가지 - 없음 / 빈 배열 / 특정 값

실습 코드에는 주석 처리된 버전들이 같이 남아 있었는데, 그걸 하나씩 지워가며 비교해보니 세 가지 패턴의 차이가 명확해졌다.

```jsx
// 1. 배열 자체가 없음 - 렌더링될 때마다 매번 실행
useEffect(function(){
    console.log(`랜더링 될 때 마다 실행`);
});

// 2. 빈 배열 - 최초 렌더링(mount) 때 딱 1번만 실행
useEffect(function (){
    console.log(`컴포넌트가 최초 랜더링할 때 실행`);
}, [])

// 3. 특정 state를 담은 배열 - 그 값이 바뀔 때만 실행
useEffect(function (){
    console.log(`num state 변경시에만 실행`);
}, [num]);
```

![useEffect의 두 번째 인자에 배열이 없을 때, 빈 배열일 때, 특정 state를 담았을 때 각각 실행 조건이 어떻게 달라지는지 비교](/images/react/useeffect_deps.svg)

세 개를 나란히 보니 규칙이 보였다 - **배열 안에 뭘 적느냐가 "이 값들 중 하나라도 바뀌면 실행해라"는 조건**이 되는 것이었다.

- 배열이 아예 없으면 "조건 없음" → 매 렌더링마다 실행
- 빈 배열 `[]`은 "감시할 값이 아무것도 없음" → 처음 딱 한 번(마운트 시점)만 실행되고 이후로는 다시 실행될 트리거가 없음
- `[num]`은 "num을 감시" → num이 바뀌어서 리렌더링될 때만 실행, 다른 이유로 렌더링돼도 무시

빈 배열이 "생성자(constructor)와 비슷하다"는 주석이 특히 도움이 됐다. 클래스형 컴포넌트를 안 배웠어도, "이 컴포넌트가 태어날 때 딱 한 번 하고 싶은 일"(초기 데이터 불러오기 같은)이 있으면 `useEffect(fn, [])`가 그 자리라는 걸 바로 이해했다.

> ✅ **핵심**: 의존성 배열이 없으면 매 렌더링마다, `[]`면 최초 1번만, `[특정 state]`면 그 state가 바뀔 때만 실행된다. 배열 안의 값들이 "감시 대상"이라고 생각하면 헷갈리지 않는다.

## 🧹 cleanup 함수 - 컴포넌트가 사라질 때 뒷정리하기

```jsx
useEffect(function() {
    console.log(`컴포넌트가 최초 랜더링할 때 실행`);
    return function(){
        console.log(`컴포넌트 삭제될 때 실행`);
    }
}, []);
```

```jsx
// App.jsx
const [comp, setComp] = useState(<Comp cnt = {1}/>);

return(
    <div>
        {comp}
        <button onClick={()=>{setComp(null)}}>component 삭제</button>
    </div>
)
```

`useEffect` 함수 안에서 **함수를 return**하면, 그게 "정리(cleanup) 함수"로 등록된다는 걸 이번에 처음 알았다. `App.jsx`에서 "component 삭제" 버튼을 누르면 `setComp(null)`이 실행되면서 화면에서 `<Comp/>`가 사라지는데, 그 순간 콘솔에 `"컴포넌트 삭제될 때 실행"`이 찍히는 걸 직접 확인했다.

왜 이런 게 필요한지 생각해보니, 컴포넌트가 살아있는 동안 타이머를 걸어두거나(`setInterval`), 이벤트 리스너를 등록하거나, 서버와 연결을 맺어놨다면 - 그 컴포넌트가 화면에서 사라진 뒤에도 그 타이머나 리스너가 계속 살아있으면 메모리 누수나 예상 못한 에러로 이어진다. cleanup 함수는 "이 컴포넌트가 하던 일을 뒷정리해라"라는 신호였다.

![useEffect가 최초 렌더링(mount)과 업데이트 시점에 실행되고, 컴포넌트가 언마운트될 때는 return한 cleanup 함수가 실행되는 생명주기](/images/react/useeffect_lifecycle.svg)

이번 실습 코드에서는 cleanup을 `[]`(마운트/언마운트 딱 1쌍)에서만 확인했는데, 사실 cleanup은 "컴포넌트가 완전히 사라질 때"뿐 아니라 **의존성 배열의 값이 바뀌어서 effect가 다시 실행되기 직전에도** 먼저 실행된다고 알고 있다. 즉 "이전 effect의 뒷정리 → 새 effect 실행"이 한 세트로 묶여서 돌아간다는 것까지는 이번에 코드로 직접 확인은 못 했지만, 다음에 `setInterval` 같은 실습이 나오면 꼭 확인해봐야겠다.

> ✅ **핵심**: `useEffect` 함수 안에서 함수를 `return`하면 그게 cleanup 함수가 된다. 컴포넌트가 화면에서 사라질 때(언마운트) 실행되며, 타이머 해제·리스너 제거 같은 뒷정리를 담당한다.

## 🤔 감이 안 왔던 부분, 다시 짚어보기

- **`useEffect(fn, [num])`에서 num이 바뀔 때, cleanup도 그 사이에 실행되나?** → 위에서 짚었듯 "effect가 다시 실행되기 전에 이전 cleanup이 먼저 실행된다"고 알고 있는데, 이번 실습 코드로는 직접 확인을 못 했다. `setInterval`을 `[num]`에 의존하게 걸어두고, num이 바뀔 때마다 이전 인터벌이 제대로 지워지는지 콘솔로 확인해보는 실험을 다음에 해봐야겠다.
- **App.jsx에서 `setComp(null)`처럼 state 안에 JSX 자체를 담아서 관리하는 방식, 언제 유용한가?** → `useState(<Comp cnt={1}/>)`처럼 컴포넌트를 통째로 state에 담아둔 게 신선했다. 보통은 `boolean` state로 `{show && <Comp/>}` 조건부 렌더링을 쓸 것 같은데, 왜 이 실습에서는 JSX 자체를 state로 뒀는지, 두 방식이 동작·재렌더링 측면에서 차이가 있는지 다음에 비교해봐야겠다.
- **의존성 배열에 여러 개를 넣으면([a, b, c]) 정확히 어떤 순서로 검사되나?** → "a 또는 b 또는 c 중 하나라도 바뀌면 실행"이라고 이해했는데, 여러 개가 동시에 바뀌는 상황에서 effect가 여러 번 실행되는지 한 번만 실행되는지는 확인이 필요하다. 다음에 두 state를 한 이벤트에서 동시에 바꾸는 코드로 직접 실험해봐야겠다.

## 💡 정리하면

`useEffect`를 배우고 나니 컴포넌트의 일생 - 태어나고(mount), 값이 바뀌고(update), 사라지는(unmount) - 각 순간에 원하는 코드를 끼워 넣을 수 있다는 큰 그림이 잡혔다. 의존성 배열이 "감시 목록"이라는 관점으로 보니 세 가지 패턴이 전부 하나의 규칙("배열 안의 값이 바뀌면 실행")으로 설명됐고, cleanup 함수 덕분에 "컴포넌트가 사라질 때 뒷정리"까지 한 세트로 관리할 수 있다는 것도 확인했다.

**오늘의 핵심 4가지**

- ⚡ `useEffect`는 렌더링이 끝난 뒤 실행되는 부수 효과(side effect) 처리용 hook이다
- 🔀 의존성 배열이 "감시 목록" - 없으면 매번, `[]`면 최초 1번(마운트), `[값]`이면 그 값이 바뀔 때만 실행
- 🧹 `useEffect` 안에서 함수를 `return`하면 cleanup 함수 - 컴포넌트가 사라질 때(언마운트) 실행되어 뒷정리를 담당
- 🧩 "컴포넌트의 일생(마운트→업데이트→언마운트)" 관점으로 보면 useEffect의 세 가지 실행 조건이 자연스럽게 이해된다
