## 🔤 LLM은 글자를 어떻게 읽을까: 토큰

LLM은 글자를 그대로 읽지 못한다. 학습할 때든 답할 때든 먼저 **숫자로 바꿔야** 한다.

학습에 쓰는 엄청나게 긴 글뭉치를 **코퍼스**라고 하고, 이 글을 **토큰(token)** 이라는 조각으로 쪼개서 각 조각에 정수 번호(ID)를 붙인다.

```
"우리 점심 메뉴는"  →  토큰으로 쪼개기  →  [17, 437, 6, 55]   (예시 숫자)
```

### 컴퓨터가 글자를 저장하는 방식

글자는 먼저 **인코딩**으로 바이트가 된다. 예를 들어 "점"은 UTF-8에서 3바이트다.

```
점  →  EC A0 90   (각 바이트는 0~255 사이의 값)
```

### 토큰은 단어가 아니다

- 토큰은 **단어가 아니라 자주 같이 나오는 글자 조각**이다. (BPE 같은 방식으로 자주 붙어 다니는 조각을 하나로 묶는다.)
- 어떻게 쪼갤지는 **모델(토크나이저)마다 다르다.**
- 한국어는 영어보다 같은 뜻에 **토큰이 더 많이 드는 경향**이 있다. 토큰 수는 곧 비용, 속도, 컨텍스트 길이 제한과 연결된다.

> LLM에게 모든 문장은 **토큰의 나열(시퀀스)** 이다.

## 🏋️ 학습: Pretrain → Posttrain

### 1단계: Pretrain (사전학습)

핵심은 **"다음 토큰 맞히기"** 다.

```
우리 점심 메뉴는 ____    ← 빈칸에 올 토큰은?
```

빈칸에 들어갈 수 있는 토큰은 많다(김치찌개, 돈까스, 비빔밥…). 그래서 신경망은 모든 토큰 후보에 **확률**을 매긴다.

학습 한 번의 흐름은 이렇다.

```
1) 토큰 시퀀스의 끝을 가리고 다음 토큰을 예측
2) 정답과 비교해서 얼마나 틀렸는지 계산 (손실, loss)
3) 역전파로 "각 가중치를 어느 방향으로 바꿔야 손실이 줄어드는지" 계산
4) 그 값으로 가중치를 조금 업데이트
5) 엄청나게 많은 글에 대해 반복
```

- 이렇게 조정되는 값이 **파라미터(가중치)** 이고, 현대 LLM은 **수십억~수천억 개 이상**이다.
- 정답이 "글에서 실제로 다음에 나온 토큰"이라서 사람이 일일이 라벨을 달 필요가 없다. 그래서 인터넷급 방대한 글로 학습할 수 있다.

### 2단계: Posttrain (사후학습)

Pretrain만 끝낸 모델은 **글을 이어 쓰는 건 잘하는데, 질문에 답하거나 지시를 따르는 건 서툴다.** 그래서 사용 목적(대화, 지시 따르기, 안전성 등)에 맞게 추가 훈련을 한다.

| 기법 | 내용 |
|---|---|
| SFT (지도 파인튜닝) | "질문 - 좋은 답변" 쌍을 보여 주며 학습 |
| RLHF, DPO 등 | 사람이 더 선호하는 답변 쪽으로 조정 |
| 강화학습 | 정답 여부 같은 보상을 기준으로 학습 |

Pretrain으로 얻은 가중치를 버리지 않고, **그 위에서 작은 폭으로 조금씩 조정**한다. 이게 파인튜닝의 기본 아이디어다. 모델마다 데이터와 기법이 달라서 결과가 다르기 때문에, 모델끼리 비교하려고 **벤치마크**를 쓴다.

## 💬 추론: 답변이 만들어지는 과정

학습이 끝난 모델을 쓰는 단계를 **추론(inference)** 이라고 한다. `우리 점심 메뉴는 ____`을 넣었을 때의 흐름이다.

```
① 토크나이저: 문장 → 토큰 ID들 [17, 437, 6, 55]
② 임베딩: 각 토큰 ID → 의미를 담은 벡터
③ 트랜스포머 레이어를 N번 통과 (layer1 → layer2 → ... → layerN)
④ 마지막 위치에서 "다음 토큰 후보별 확률" 계산
⑤ 확률에 따라 토큰 하나 선택 (예: "김치찌개")
⑥ 선택한 토큰을 입력 끝에 붙이고 ①~⑤를 반복 → 한 토큰씩 문장이 완성됨
```

답변은 한 번에 나오는 게 아니라 **토큰을 하나씩 이어 붙이며** 만들어진다. 스트리밍 화면에서 글자가 조금씩 나오는 것도 이 때문이다.

**temperature**는 ⑤에서 토큰을 고를 때의 **무작위성**을 조절하는 값이다. 지난번에 겪은 temperature 오류도 이 설정과 관련된 것이었다.

### 트랜스포머와 Attention

트랜스포머의 핵심은 **attention**이다. 문장 속 토큰들이 **서로 얼마나 관련 있는지**를 계산해서, 각 토큰의 의미를 문맥에 맞게 갱신한다.

```
"은행에 가서 돈을 찾았다"  →  '은행'이 '돈'과 관련 있음을 반영해 뜻을 정함
```

`[17, 437, 6, 55]`처럼 토큰이 여러 개 있으면 서로의 관계를 계속 계산하는 셈이다. GPT 같은 생성 모델은 아직 만들지 않은 뒤쪽 토큰은 볼 수 없으니 **앞에 나온 토큰들만** 참고한다.

### 추론 중에는 학습되지 않는다

> 추론은 모델을 **쓰는 것**이고, 모델(가중치)을 바꾸는 건 **학습**뿐이다.

대화하면서 뭔가 알려 줘도 모델의 가중치는 변하지 않는다. 그런데도 프롬프트에 예시나 문서를 넣으면 답이 달라지는데, 이건 모델이 바뀐 게 아니라 **입력(컨텍스트)이 바뀌었기 때문**이다. 프롬프트와 RAG가 통하는 이유가 바로 이것이다.

## ⚡ KV Cache

토큰을 하나씩 만드는 구조라면, 매번 앞의 토큰들을 처음부터 다시 계산하는 건 너무 낭비다.

attention 계산에서 각 토큰은 **Key와 Value**라는 값을 만드는데, 이미 처리한 토큰의 Key/Value는 다음 토큰을 만들 때도 똑같다. 그래서 **저장해 두고 재사용**한다. 이게 **KV Cache**다.

| | 캐시 없이 | KV Cache 사용 |
|---|---|---|
| 새 토큰을 만들 때 | 앞 토큰들을 전부 다시 계산 | **새 토큰 것만** 계산하고 나머지는 저장값 사용 |
| 속도 | 느림 | 빠름 |
| 대가 | 없음 | **메모리**를 차지 (컨텍스트가 길수록 커짐) |

컨텍스트가 길수록 GPU 메모리를 많이 쓰는 이유 중 하나다.

## 🧭 Prompt vs RAG vs Fine-tuning

모델을 바꾸는 건 학습(파인튜닝)뿐이고, 프롬프트와 RAG는 **입력을 바꿔서** 결과를 바꾸는 방식이다. 그래서 문제의 종류에 따라 고르는 게 달라진다.

| | 프롬프트(지침) | RAG | 파인튜닝 |
|---|---|---|---|
| 바꾸는 것 | 입력의 지시문 | 입력에 넣는 **참고 자료** | **모델 가중치** |
| 잘 맞는 문제 | 역할, 형식, 규칙 지정 | 사내·고객별 문서, 최신 정보, **근거 기반 답변** | 반복되는 형식·말투·행동, 특화 태스크, 비용 최적화 |
| 비용·난이도 | 가장 낮음 | 중간 (검색 시스템 구축) | 가장 높음 (데이터, 학습, 평가) |
| 정보 갱신 | 프롬프트 수정 | **문서만 갱신** | 다시 학습해야 함 |
| 출처 제시 | 어려움 | **가능** | 어려움 |

### 파인튜닝의 "비용 최적화"

- 큰 모델이 하던 일을 **작은 모델에 파인튜닝**해서 더 싸고 빠르게 처리
- 매번 길게 넣던 지침이나 예시를 모델에 학습시켜서 **프롬프트를 짧게** 만들기

### 고르는 순서

```
1. 프롬프트로 먼저 시도  (가장 싸고 빠름)
2. 모델이 모르는 문서나 최신 정보가 필요하면 → RAG
3. 형식·말투·행동이 계속 흔들리거나, 비용·속도를 줄여야 하면 → 파인튜닝
```

셋은 택일이 아니라 **조합**해서 쓰는 경우가 많다. (예: 파인튜닝한 작은 모델 + RAG + 프롬프트)

## 🛠️ 헷갈렸던 부분

**1) 토큰이 곧 단어 아닌가?**
→ 아니다. 토큰은 자주 쓰이는 글자 조각이고, 모델마다 쪼개는 방식이 다르다. UTF-8 바이트가 그 바탕에 있지만, 토큰은 그 위에서 조각을 묶은 단위다.

**2) 학습할 때 "틀리면 다시 추론"하는 건가?**
→ 다시 추론하는 게 아니라, 틀린 정도(손실)를 계산해서 **역전파로 가중치를 고치는** 과정이다.

**3) 대화하면서 알려 주면 모델이 배우는 건가?**
→ 아니다. 추론 중에는 가중치가 변하지 않는다. 입력에 들어간 내용이 답에 영향을 줄 뿐이고, 그게 프롬프트와 RAG의 원리다.

**4) 새로운 지식을 넣으려면 파인튜닝이 맞나?**
→ 지식을 안정적으로 넣는 용도로는 RAG가 더 잘 맞는다. 파인튜닝은 **행동과 형식을 다듬는 용도**에 더 어울린다.

## 💡 정리하면

| 개념 | 한 줄 요약 |
|---|---|
| 토큰 | 글자 조각. 단어와 다르고 모델마다 쪼개는 방식이 다름 |
| Pretrain | 방대한 글로 **다음 토큰 맞히기**를 반복해 가중치를 학습 |
| Posttrain | 사용 목적에 맞게 지시 따르기, 선호, 안전성 등을 추가 학습 |
| 역전파 | 손실을 줄이는 방향으로 **가중치를 얼마나 바꿀지** 계산 |
| 추론 | 토큰을 하나씩 생성해 답변을 만드는 과정 (가중치는 안 바뀜) |
| Attention | 토큰끼리의 관련도를 계산해 문맥을 반영 |
| KV Cache | 이미 계산한 Key/Value를 저장해 재계산을 피함 (속도↑, 메모리↑) |
| 프롬프트 | 지시와 형식을 입력으로 조정 |
| RAG | 근거 문서를 검색해 입력에 넣음 (최신·사내 정보, 출처) |
| 파인튜닝 | 가중치를 바꿔 형식·행동을 일관되게, 비용을 줄임 |

- 모델이 **모르는 지식**은 RAG, **행동과 형식**은 파인튜닝, 둘 다 **먼저 프롬프트로** 시도한다.
- 결국 LLM을 잘 쓴다는 건 "모델을 바꿀 것인가, 입력을 바꿀 것인가"를 문제에 맞게 고르는 일이라는 걸 정리하면서 알게 됐다.
