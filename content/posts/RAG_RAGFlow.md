## 🧭 RAGFlow는 어떤 도구?

수업의 핵심 문장은 이거였다.

> 다른 넷은 **'코드로 조립하는 프레임워크'**, RAGFlow는 **'띄워서 쓰는 엔진'**

- 라이브러리가 아니라 **Docker로 띄우는 엔드투엔드 RAG 엔진**
- 문서 파싱 → 청킹 → 임베딩 → 검색 → 생성 → 인용까지 **한 패키지**
- **웹 UI와 REST API**를 함께 제공
- 핵심 차별점은 **깊은 문서 이해**(레이아웃, 표, 스캔 OCR)

한 줄 정체성은 **"띄워서 쓰는 완제품 RAG"**. 비개발 팀이나 복잡한 문서에 강하고, 대신 코드로 세밀하게 제어하는 건 제한적이다.

## 📄 핵심 특징: 문서 이해 중심

| 특징 | 설명 |
|---|---|
| Deep Document Understanding | 레이아웃, 표, 스캔 OCR의 **구조까지 보존**해서 파싱 → 청크 품질↑ |
| 청킹 템플릿 | 문서 유형(논문, 매뉴얼, 법령, QA)별로 맞춰진 청킹 프리셋 제공 |
| 인용 시각화 | 답변 근거를 **원문의 위치로 하이라이트** → 검증, 신뢰↑ |

RAG 품질은 결국 **"문서를 얼마나 잘 읽어서 쪼개느냐"**에서 많이 갈린다. 표가 있는 PDF를 단순히 글자만 뽑으면 표의 행과 열이 뒤섞여서 의미가 사라진다. RAGFlow는 이 파싱 단계에 힘을 쏟은 도구다.

그리고 인용 시각화는 내가 쓴 환각 관련 글과도 연결된다. 답변이 **원문의 어디에서 나왔는지** 눈으로 확인할 수 있으면 근거 없는 답변을 걸러내기 쉽다.

## 🐳 구동 방식: Docker + 웹UI/API

```bash
git clone https://github.com/infiniflow/ragflow && cd ragflow/docker
docker compose up -d      # 엔진 + 웹UI + API
```

그다음은 웹 UI에서 클릭으로 진행한다.

```
Knowledge Base 생성 → 문서 업로드 → Chat 생성 → 질의(+인용)
```

| 단계 | 하는 일 |
|---|---|
| Knowledge Base 생성 | 문서를 담을 지식베이스 만들기 |
| 문서 업로드 | 파일을 올리면 파싱·청킹이 진행됨 (Parsing Status 확인) |
| Chat 생성 | 그 지식베이스를 쓰는 챗봇 만들기 |
| 질의 | 질문하면 답변과 함께 인용이 표시됨 |

수업에서는 **메모리 요구가 커서 직접 실행하지 않고** GitHub 페이지에서 기능만 확인했다. 자체 호스팅 사전 준비 사항은 다음과 같았다.

| 항목 | 요구 사양 |
|---|---|
| CPU | 4 cores 이상 |
| RAM | 16 GB 이상 |
| Disk | 50 GB 이상 |
| Docker | 24.0.0 이상, Docker Compose v2.26.1 이상 |

프레임워크는 노트북에서 가볍게 돌렸는데, RAGFlow는 요구 사양부터 "서비스를 하나 띄우는" 수준이다. 이 점이 가장 큰 차이로 느껴졌다.

## ⚖️ 강점과 약점

| 구분 | 내용 |
|---|---|
| 강점 | 문서 파싱 품질(표, 스캔), 웹 UI, 청킹 템플릿, 인용 — **비개발자도 구축 가능** |
| 약점 | 무겁다(Docker, 리소스), 코드 세밀 제어 제한, 커스텀 유연성↓ |

## 🛠️ 헷갈렸던 부분

**1) 그럼 RAGFlow는 코딩이 필요 없나?**
→ 기본적인 사용은 웹 UI로 가능하다. 다만 REST API도 제공해서 다른 서비스와 연결할 수는 있다. 반대로 내부 동작을 코드로 바꾸고 싶으면 한계가 있다.

**2) 언제 RAGFlow를 쓰고, 언제 프레임워크를 쓰나?**

| 상황 | 선택 |
|---|---|
| 스캔 문서, 표가 많고 비개발 팀이 운영해야 함 | RAGFlow |
| 검색 로직을 직접 설계하고 코드로 통합해야 함 | LlamaIndex, Haystack 등 |

**3) 검색 품질도 RAGFlow가 제일 좋은가?**
→ 꼭 그렇지는 않다. 같은 코퍼스로 비교한 수업 실험에서 검색 품질은 프레임워크보다 **임베딩 같은 구성요소가 결정**했다. RAGFlow의 강점은 검색 알고리즘보다 **문서를 읽고 쪼개는 단계의 품질과 편의성**이다.

## 💡 정리하면

| 개념 | 한 줄 요약 |
|---|---|
| RAGFlow | Docker로 띄우는 엔드투엔드 RAG 엔진 |
| Deep Document Understanding | 레이아웃, 표, 스캔 OCR 구조를 살린 파싱 |
| 청킹 템플릿 | 문서 유형별 청킹 프리셋 |
| 인용 시각화 | 답변 근거를 원문 위치로 하이라이트 |

- RAGFlow는 우열이 아니라 **결이 다른 도구**다. 코드로 조립하는 프레임워크가 아니라 **띄워서 쓰는 엔진**이다.
- **복잡한 문서(스캔, 표)와 비개발 팀 운영**에 강하다.
- 대신 **무겁고, 코드로 세밀하게 제어하기 어렵다.**
