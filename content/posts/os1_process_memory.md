## 📖 프로세스란 - 프로그램과의 차이

| 구분 | 의미 |
|---|---|
| Program | 디스크에 저장된 실행 파일 (그냥 데이터 덩어리) |
| Process | 그 파일이 실행되어 CPU·메모리를 할당받은 상태 |

Chrome 설치 파일은 프로그램이고, 더블클릭해서 실행된 Chrome은 프로세스다. 이 둘의 차이를 처음엔 "그냥 이름만 다른 거 아닌가" 싶었는데, **"자원을 할당받았는가"**가 핵심 기준이라는 걸 알고 나니 명확해졌다. 프로그램은 몇 번을 실행하든 디스크에 있는 파일 자체는 그대로지만, 실행할 때마다 운영체제가 별도의 메모리 공간과 프로세스 식별자를 새로 만들어준다 - 그래서 크롬을 두 번 실행하면(정확히는 새 창을 열면) 서로 다른 프로세스가 될 수 있는 것이다.

> ✅ **핵심**: 프로세스는 "프로그램 + 운영체제가 할당한 자원(CPU, 메모리)"이다. 프로그램은 정적인 파일, 프로세스는 그 파일이 실행되어 살아있는 상태다.

## ⚙️ 프로그램이 프로세스가 되는 순간 무슨 일이 벌어지나

여기서 궁금했던 건 "그럼 실행 버튼을 누르는 순간 정확히 뭐가 일어나는가"였다. 찾아보니 운영체제는 프로세스마다 **PCB(Process Control Block)**라는 정보 카드를 하나씩 만든다. PCB에는 대략 이런 정보가 들어간다:

- 프로세스 ID(PID) - 프로세스를 구분하는 고유 번호
- 프로세스 상태 (Ready/Running/Waiting 등 - 다음 글에서 다룰 내용)
- CPU 레지스터 값 - 문맥 전환(context switching) 시 여기에 저장해뒀다가 복원
- 메모리 정보 - 이 프로세스가 어느 메모리 영역을 쓰고 있는지에 대한 포인터

즉 "프로그램을 실행한다"는 건 **디스크의 코드를 메모리에 올리고, 그 메모리를 가리키는 PCB를 만들어서 운영체제가 관리 목록에 등록하는 것**이다. 이 관점으로 보니 뒤에서 배울 프로세스 상태 전이(New → Ready → Running ...)도 결국 이 PCB 안의 "상태" 값이 바뀌는 것뿐이라는 걸 미리 짐작할 수 있었다.

> ✅ **핵심**: 프로세스가 생성되면 운영체제는 PCB(프로세스 관리용 정보 카드)를 만들어서 PID, 상태, 레지스터 값, 메모리 위치를 추적한다.

## 🧱 프로세스의 메모리 구조 - 4개 영역

프로세스 하나가 쓰는 메모리는 아무렇게나 섞여 있는 게 아니라 4개 영역으로 딱 나뉘어 있다.

| 영역 | 역할 | 특징 |
|---|---|---|
| Code | 실행 코드(명령어) | 읽기 전용 - 실행 중 실수로 코드가 바뀌는 걸 방지 |
| Data | 전역 변수, 정적(static) 변수 | 프로그램 시작부터 종료까지 유지 |
| Heap | 동적으로 생성되는 데이터 | 크기가 실행 중에 변함, 직접(또는 GC로) 관리 |
| Stack | 함수 호출 정보(지역변수, 매개변수) | 함수가 끝나면 자동으로 정리됨 |

```python
user = {"name": "Daniel", "age": 12}  # 이 객체는 Heap에 생성된다

def hello():
    name = "Daniel"  # name은 Stack에 쌓인다
hello()  # 함수가 끝나면 Stack의 name도 같이 사라진다
```

이 4개를 처음엔 그냥 암기하려고 했는데 계속 까먹었다. 그런데 **"함수 호출 → Stack, 객체 생성 → Heap, 전역 변수 → Data"**처럼 실제 코드 동작과 짝지어서 보니까 왜 그 영역에 저장되는지가 이해되면서 저절로 외워졌다. 특히 `Code`가 읽기 전용인 이유도 처음엔 그냥 규칙인 줄 알았는데, "실행 중인 명령어 자체가 바뀌어버리면 프로그램이 어떻게 동작할지 예측할 수 없어진다"고 생각하니 왜 보호해야 하는지 납득이 갔다.

## 🔄 Stack과 Heap이 서로를 향해 자라는 이유

이번에 제일 "아하" 했던 부분이다. Stack과 Heap은 그냥 각자 정해진 크기만큼 쓰는 게 아니라, **메모리 공간의 양 끝에서 서로를 향해 자란다.**

![Stack은 높은 주소에서 아래로, Heap은 낮은 주소에서 위로 자라며 서로를 향해 다가간다](/images/os/memory_layout.svg)

- **Stack**은 높은 주소에서 시작해서 **아래로** 자란다 - 함수를 호출할 때마다(특히 재귀 호출) 한 칸씩 쌓인다.
- **Heap**은 Data 영역 바로 위, 낮은 주소 쪽에서 시작해서 **위로** 자란다 - `malloc`이나 파이썬 객체 생성처럼 동적 할당을 할 때마다 늘어난다.

이렇게 서로 반대 방향에서 자라게 설계한 이유를 생각해보니, **"둘 다 크기가 실행 전엔 알 수 없다"**는 공통점 때문인 것 같다. Code/Data는 프로그램을 실행하기 전에 이미 크기가 정해져 있지만, 얼마나 깊이 함수를 호출할지(Stack)나 얼마나 많은 객체를 만들지(Heap)는 실행해봐야 안다. 그러니 한쪽에 크기를 미리 정해두는 대신, 가운데 빈 공간을 공유하면서 각자 필요한 만큼 자라게 하는 게 합리적인 설계였다.

그리고 여기서 **Stack Overflow**가 왜 일어나는지도 명확해졌다. 재귀 함수가 종료 조건 없이 계속 자기 자신을 호출하면 Stack이 끝없이 아래로 자라다가, 결국 Heap이 차지한 영역과 부딪힌다 - 그 순간이 "Stack Overflow" 에러다. 이름만 알고 있었는데, 그림으로 그려보니 왜 "Overflow(넘침)"라는 단어를 쓰는지도 감이 왔다.

> ✅ **핵심**: Stack은 높은 주소에서 아래로, Heap은 낮은 주소에서 위로 자란다. 둘 다 실행 전엔 크기를 예측할 수 없기 때문에 이런 구조로 설계됐고, 서로 충돌하면 Stack Overflow가 발생한다.

## 🤔 감이 안 왔던 부분, 다시 짚어보기

- **파이썬은 왜 Heap 메모리 누수를 신경 안 써도 되나?** → C처럼 `malloc`으로 직접 할당한 메모리는 `free`로 직접 해제해야 하는데, 파이썬은 가비지 컬렉터(GC)가 더 이상 참조되지 않는 객체를 자동으로 정리해준다. 그래서 "메모리 누수"라는 말을 파이썬 코드에선 잘 안 쓰는 것 같은데, 정확히는 "안 나는 게 아니라 GC가 대신 막아주는 것"이라고 이해하는 게 맞을 것 같다. 다만 순환 참조처럼 GC도 못 잡는 케이스가 있다고 들었으니, 다음에 그 예시를 직접 찾아봐야겠다.
- **Stack 크기는 얼마나 될까?** → 무한정 늘어날 수 있는 게 아니라 운영체제/스레드마다 정해진 한도가 있다고 한다. 리눅스에서 `ulimit -s` 명령으로 현재 Stack 크기 한도를 확인할 수 있다는데, 다음에 직접 재귀 함수를 만들어서 몇 번째 호출에서 Stack Overflow가 나는지 실험해봐야겠다.

## 💡 정리하면

이번 정리에서 확실해진 건, 운영체제가 메모리를 4개 영역으로 나눈 게 임의의 규칙이 아니라 **"수명과 크기 예측 가능성"에 따른 합리적인 구분**이라는 점이었다. Code/Data처럼 실행 전에 크기가 정해지는 것과, Stack/Heap처럼 실행 중에 크기가 변하는 것을 분리하고, 후자 둘은 서로 마주 보며 자라게 해서 공간을 효율적으로 나눠 쓴다.

**오늘의 핵심 4가지**

- 📖 프로세스 = 프로그램 + 운영체제가 할당한 자원. PCB로 관리된다
- 🧱 메모리는 Code(읽기전용) / Data(전역) / Heap(동적) / Stack(함수호출) 4개 영역으로 나뉜다
- 🔄 Stack은 위→아래, Heap은 아래→위로 자라며 서로를 향해 다가간다
- 💥 Stack Overflow는 이 둘이 충돌할 때 발생한다 - 대개 종료 조건 없는 재귀 호출이 원인
