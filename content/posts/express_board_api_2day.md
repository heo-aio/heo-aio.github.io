## 프로젝트 구조부터 잡기 - index.js와 routes를 나누는 이유

처음엔 `index.js` 하나에 다 때려박아도 되지 않나 싶었다. 근데 게시글 관련 기능이 4개(리스트/상세/글쓰기/삭제)나 되고, 나중에 회원 기능까지 붙일 걸 생각하면 한 파일에 다 넣는 게 답이 아니었다.

```
board-api/
  index.js
  routes/
    posts.js
    auth.js
  data/
    posts.js
    users.js
  middlewares/
    auth.js
```

`index.js`는 "서버를 어느 포트에서 켤지, 어떤 라우터를 어디에 연결할지"만 담당하고, 실제 로직은 `routes` 안에 있는 구조로 잡았다. 처음엔 `index.js`가 "API 정의의 메인"이라고 생각했는데, 정확히는 **목차** 역할이고 **본문**은 각 라우터 파일에 있는 거였다.

```js
app.use("/posts", require("./routes/posts"));
app.use("/users", require("./routes/auth"));
```

`app.use("/posts", posts)`가 실제로 연결(마운트)해주는 코드고, 라우터 파일 안에서 쓴 `"/"`, `"/:id"` 같은 경로는 이 마운트 경로 뒤에 자동으로 붙는다는 걸 여기서 처음 체감했다. `router.get("/:id", ...)`가 실제로는 `GET /posts/:id`로 동작하는 이유가 이거였다.

> ✅ **핵심**: `index.js`는 라우터를 어디에 연결할지 배치하는 관제탑이고, 실제 동작(로직)은 `routes/*.js` 파일 안에 있다. 자원(resource) 단위로 파일을 나누면 나중에 기능이 늘어나도 어디를 봐야 할지 헷갈리지 않는다.

## 제일 많이 헤맨 지점 - 라우트 순서 문제

검색 기능(`/posts/search?title=...`)을 만들다가 진짜 오래 헤맸다. 처음 짠 코드는 이랬다.

```js
router.get("/:id", (req, res) => { ... })   // 상세보기
router.get("/search", (req, res) => { ... }) // 검색 (아래에 위치)
```

`GET /posts/search`로 요청을 보냈는데 자꾸 "글이 없습니다" 응답이 왔다. 처음엔 검색 로직이 잘못됐나 싶어서 필터링 코드를 계속 고쳤는데, 문제는 그게 아니었다.

Express는 **라우트를 위에서부터 순서대로** 매칭한다. `:id`는 어떤 문자열이든 다 받아버리는 파라미터라서, `"search"`라는 글자 자체가 `id` 값으로 들어가버렸다. `parseInt("search")`는 `NaN`이 되고, 배열에서 못 찾으니 "글이 없습니다"가 뜬 거였다. `/search` 라우트는 코드상 존재하는데 **한 번도 실행될 기회가 없었던** 거다.

```js
// 수정: 고정 경로를 :id보다 위로
router.get("/search", (req, res) => { ... })
router.get("/:id", (req, res) => { ... })
```

거기다 콜론을 실수로 안 뺀 채로 `router.get("/:search", ...)`라고 쓴 적도 있었는데, 이러면 `:search`도 그냥 또 다른 동적 파라미터가 돼버려서 `/search`라는 글자를 정확히 매칭하지 못한다. 콜론 유무가 "고정 경로 vs 동적 경로"를 가르는 거였다.

> ✅ **핵심**: 구체적인(고정) 경로는 항상 `:파라미터`가 들어간 동적 경로보다 위에 둬야 한다. `:id` 같은 파라미터는 거의 모든 문자열을 다 잡아먹는 그물이라고 생각하면 순서가 왜 중요한지 감이 온다.

## 응답을 두 번 보내는 버그 - return을 깜빡했을 때

검색 라우트를 `if/else`로 짜다가 이런 에러를 처음 만났다.

```
Error: Cannot set headers after they are sent to the client
```

원인 코드는 이거였다.

```js
if (title) {
    result = posts.filter(...)
} else {
    res.send("검색 결과가 없습니다.");
}

res.json({ "검색 결과": result }); // else를 타고 나와도 이 줄이 또 실행됨
```

`else` 블록에서 응답을 한 번 보냈는데, `return`이 없어서 코드가 계속 아래로 흘러가 `res.json()`이 또 실행됐다. Express는 응답을 한 번만 보낼 수 있어서 두 번째 응답 시도에서 에러가 났다.

```js
} else {
    return res.send("검색 결과가 없습니다."); // return으로 확실히 끝내기
}
return res.json({ "검색 결과": result });
```

이후로 조건 분기가 있는 라우트를 짤 때마다 "각 분기마다 return을 붙였는가"를 습관적으로 체크하게 됐다. 글쓰기, 상세보기, 삭제, 회원가입, 로그인 라우트 전부 다 같은 패턴으로 한 번씩 걸렸다.

> ✅ **핵심**: 라우터 핸들러 안에서 응답이 여러 갈래로 나뉠 때는 각 분기마다 반드시 `return`을 붙여서 "여기서 끝"이라고 명시해야 한다. 안 그러면 다음 코드가 이어서 실행되다가 응답 중복 에러가 난다.

## find, findIndex, indexOf - 뭘 언제 써야 하나

삭제 기능을 짜면서 `indexOf`를 써보려다가 막혔다.

```js
posts.indexOf({ id: 1, title: "첫 번째 글" }); // -1, 못 찾음
```

`indexOf`는 값 자체가 `===`로 정확히 일치해야 찾는데, 새로 만든 객체는 내용이 같아도 메모리 주소가 달라서 절대 못 찾는다. 우리 `posts`는 객체 배열이고 `id`라는 속성값으로 찾아야 하니까 애초에 `indexOf`를 쓸 수 있는 상황이 아니었다.

```js
const idx = posts.findIndex((item) => item.id === id); // 조건으로 찾기
```

`find()`는 조건에 맞는 요소 **자체**를 반환하고(상세보기에서 씀), `findIndex()`는 조건에 맞는 요소의 **위치**를 반환한다(삭제에서 씀, `splice`로 지우려면 위치가 필요하니까). 그리고 못 찾았을 때 `find()`는 `undefined`, `findIndex()`는 `-1`을 반환한다는 차이도 여기서 정리됐다.

덤으로 `undefined`와 `null`도 헷갈렸었는데, `find()`가 실패하면 `null`이 아니라 항상 `undefined`를 반환한다는 걸 모르고 `=== null`로 비교했다가 조건이 영원히 `false`가 되는 버그도 겪었다. `undefined`는 JS가 자동으로 부여하는 "없음" 상태고, `null`은 개발자가 의도적으로 넣어야 나오는 값이라는 차이였다.

> ✅ **핵심**: 객체 배열에서 특정 속성값으로 찾을 땐 `find`/`findIndex`, 단순 값 배열에서 값 자체로 찾을 땐 `indexOf`. `find()`가 실패하면 `undefined`를 반환하지, `null`을 반환하지 않는다.

## JWT 인증 붙이기 - 미들웨어 next() 빠뜨린 사건

선택 기능으로 회원가입/로그인/JWT 인증까지 붙였다. 로그인은 `bcrypt.compare()`로 비밀번호를 검증하고 `jwt.sign()`으로 토큰을 발급하는 흐름이었는데, 여기서 처음엔 `bcrypt.compare`가 "복호화"인 줄 알았다. 근데 bcrypt는 단방향 암호화라 복호화 자체가 불가능하고, `compare`는 입력값을 **같은 방식으로 다시 암호화해서 결과가 일치하는지 비교**하는 거였다. 지문 인식이 저장된 지문 데이터를 복원하는 게 아니라 매번 새로 스캔해서 비교하는 것과 같은 원리라고 이해하니 감이 왔다.

인증 미들웨어를 만들 때는 이런 실수를 했다.

```js
function getToken(req, res, next) {
    const token = req.headers.authorization;
    if (!token) {
        return res.status(401).json({ success: false, msg: "권한이 없습니다." });
    }
    try {
        const info = jwt.verify(token, JWT_SECRET);
        // next()가 없음!
    } catch (e) {
        return res.status(401).json({ success: false, msg: "유효하지 않은 토큰입니다." });
    }
}
```

토큰이 유효하지 않을 때는 `res.status(401)`로 응답하면서 멈추는 게 맞는데, **토큰이 정상일 때 다음 단계로 넘어가라는 `next()` 호출이 빠져있었다.** 그래서 인증에 성공한 요청도 응답을 못 받고 그대로 멈춰버렸다. 에러도 안 떠서 한참 "왜 응답이 안 오지" 하고 헤맸다.

```js
try {
    const info = jwt.verify(token, JWT_SECRET);
    req.user = info;
    next(); // 통과시켜야 실제 라우터 핸들러로 넘어감
} catch (e) {
    return res.status(401).json({ success: false, msg: "유효하지 않은 토큰입니다." });
}
```

미들웨어의 모든 코드 경로는 `next()` 아니면 `res.xxx()` 둘 중 하나로 끝나야 한다는 걸 몸으로 배웠다. 이걸 만든 다음 `router.get("/", getToken, (req, res) => {...})`처럼 라우트마다 미들웨어를 끼워 넣어서, 리스트/상세/글쓰기를 로그인한 사람만 쓸 수 있게 막았다.

![클라이언트가 Authorization 헤더에 토큰을 담아 요청을 보내면, 인증 미들웨어가 토큰 유무와 유효성을 검증한 뒤 next()로 통과시키거나 401로 즉시 응답하는 흐름도](/images/express/board_api_jwt_middleware_flow.svg)

> ✅ **핵심**: 미들웨어는 `next()`를 호출해야 다음 핸들러로 넘어간다. `next()`도 안 부르고 응답도 안 보내면 요청이 그대로 멈춘 채 아무 반응이 없다 - 에러조차 안 나서 오히려 발견하기 까다로운 버그였다.

## 에러 없이 조용히 잘못 동작하는 버그 - 오타 하나의 위력

회원가입 중복 체크 로직을 짜다가 이런 코드를 썼다.

```js
const duplication = users.find((item) => {
    return item.uesrId === userId; // uesr... 오타
});
```

`userId`를 `uesrId`로 잘못 쳤는데, JS는 존재하지 않는 속성에 접근해도 에러를 안 던지고 그냥 `undefined`를 반환한다. `undefined === userId`는 항상 `false`니까 `find()`는 절대 못 찾고, 중복 체크 자체가 있으나 마나 한 상태로 계속 회원가입이 성공해버렸다. 실행은 멀쩡하게 되고 에러 로그도 없어서, 직접 `console.log(users)`로 실제 데이터를 찍어보고 나서야 오타를 발견했다.

> ✅ **핵심**: 오타는 논리 오류라서 컴파일/런타임 에러가 안 난다. 객체를 만들 때 쓴 속성 이름과 나중에 읽을 때 쓴 이름이 글자 하나까지 똑같은지 대조하는 습관, 그리고 의심되면 바로 `console.log`로 실제 데이터를 찍어보는 습관이 필요하다는 걸 느꼈다.

## 감이 안 왔던 부분, 다시 짚어보기

- **원시타입 vs 참조타입 전달 방식** - `nextId` 값을 그냥 export하면 받는 쪽에서 증가시켜도 원본이 안 바뀌어서, 함수(`getNextId: () => nextId++`)로 감싸서 내보내야 했다. 반면 `posts` 배열은 export만 해도 `push()`가 원본에 그대로 반영됐다. 원시타입은 값이 복사되고 객체/배열은 참조가 공유된다는 개념 자체는 이해했는데, 이게 클로저랑 정확히 어떻게 맞물리는지는 다음에 더 파봐야 할 것 같다.
- **`JWT_SECRET`을 왜 고정값으로 둬야 하는지** - 처음엔 `crypto.randomBytes()`로 서버 켤 때마다 새로 만들어도 되는 줄 알았는데, 로그인할 때 서명한 키랑 검증할 때 쓰는 키가 달라지면 토큰이 항상 무효 처리된다는 걸 뒤늦게 알았다. 지금은 파일 하나에서 한 번만 생성해서 공유하는 식으로 넘어갔는데, 실무에서 `.env`로 관리하는 것까지는 이번에 안 해봐서 다음 프로젝트에서 시도해봐야겠다.
- **DB 없이 메모리 배열로만 만든 한계** - 서버를 끄면 데이터가 다 날아간다는 걸 당연히 알면서도 막상 재현해보니 체감이 확실히 됐다. 다음 단계로 JSON 파일 저장이나 MongoDB 연결까지 해봐야 진짜 "서비스"라고 부를 수 있을 것 같다.

## 정리하면

강의 들을 때는 그냥 흘려들었던 개념들이, 직접 손으로 치면서 에러를 만나고 나서야 진짜 이해가 됐다. 특히 "동작은 하는데 왜 이상하게 동작하지" 싶었던 버그들(라우트 순서, return 누락, next() 누락, 오타)이 전부 겉으로는 티가 안 나는 종류라서, 이런 걸 스스로 의심하고 찾아내는 감각 자체가 이번 2일의 진짜 수확이었다.

**오늘의 핵심 5가지**

- 🧭 라우트는 위에서부터 순서대로 매칭된다 - 고정 경로는 항상 `:파라미터` 경로보다 위에
- 🔁 조건 분기로 응답이 갈릴 땐 매 분기마다 `return`을 붙여서 흐름을 확실히 끊어야 한다
- 🔍 객체 배열에서 조건으로 찾을 땐 `find`/`findIndex`, `find` 실패 시 반환값은 `null`이 아니라 `undefined`
- 🛂 미들웨어는 `next()` 호출 아니면 응답 전송, 둘 중 하나로 반드시 끝나야 한다
- 🐛 오타는 에러를 안 띄우고 조용히 실패한다 - 의심되면 `console.log`로 실제 데이터를 찍어보는 게 제일 빠르다

다음엔 이 구조 그대로 comment API나 todo API처럼 다른 자원에 똑같은 패턴을 반복 연습해보고, 여유가 되면 MongoDB 연결이랑 FastAPI로도 같은 프로젝트를 한 번 더 만들어봐야겠다.
