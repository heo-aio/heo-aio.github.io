## 📚 JSX란 - 태그를 값처럼 다루기

```js
// 본래 js에서는 태그는 문자열에 담는다.
// jsx는 태그 자체를 담을 수 있다.
// let js = ''<h3>Hello World</h3>';
// let jsx = <h3>Hello World</h3>;
```

실습 코드 주석에 적혀 있던 이 두 줄 비교가 핵심이었다. 원래 JS에서 HTML을 다루려면 `'<h3>Hello World</h3>'`처럼 **문자열**로 감싸야 한다. 그런데 JSX는 따옴표 없이 태그를 그대로 변수에 담을 수 있다. 이게 어떻게 가능한지 궁금했는데, 답은 **JSX가 결국 함수 호출로 변환(transpile)되기 때문**이었다.

`<h3>Hello World</h3>`는 빌드 과정에서 Babel을 거쳐 `React.createElement('h3', null, 'Hello World')`라는 평범한 함수 호출로 바뀐다. 함수 호출은 당연히 값을 반환하니까 변수에 담을 수도, 조건문의 결과로 쓸 수도 있는 것이었다. "태그가 왜 값처럼 동작하지?"라는 의문이 "함수 호출 결과니까 당연히 값이지"로 바뀌는 순간이었다.

![JSX 코드가 Babel을 거쳐 React.createElement 함수 호출로 변환되고, 최종적으로 실제 DOM으로 렌더링되는 흐름](/images/react/jsx_transpile_flow.svg)

```jsx
return (<>
  <div className="App">
    <h3>안녕하세요 리액트에 잘 오셨습니다.</h3>
  </div>
  <div>
    {name}/{gender}/{age} {/*자바스크립트 관련은 {}로 영역을 잡아준다.*/}
    <br/> {/*태그는 닫히지 않으면 문법 에러 발생*/}
  </div>
</>);
```

여기서 두 가지를 같이 짚고 넘어갔다.

- **`{}` 문법**: JSX 안에서 순수 HTML이 아니라 JS 값/표현식을 쓰고 싶을 때 `{}`로 감싼다. `{name}`처럼 변수든, `{1+1}`처럼 연산이든 다 가능하다. 다만 **표현식(expression)만** 가능하고 `if`, `for` 같은 **문장(statement)**은 들어갈 수 없다 — 이 이유는 바로 다음 섹션에서 이어진다.
- **`<>...</>` (Fragment)**: `return`은 값을 하나만 반환할 수 있는데, 컴포넌트 안에 최상위 태그가 여러 개면 문법 에러가 난다. 그렇다고 매번 불필요한 `<div>`로 감싸면 실제 DOM에 의미 없는 태그가 계속 쌓인다. Fragment(`<>`)는 "이 여러 개를 하나로 묶어서 반환하되, 실제 DOM에는 흔적을 남기지 않는" 빈 껍데기 역할을 한다.
- **태그는 반드시 닫혀야 한다**: `<br/>`처럼 self-closing이든 `<div></div>`처럼 닫는 태그든, HTML과 달리 JSX는 닫지 않은 태그를 허용하지 않는다. 이것도 결국 JSX가 함수 호출로 변환되기 때문 - 함수 호출 괄호가 안 닫히면 에러가 나는 것과 같은 이치다.

> ✅ **핵심**: JSX는 Babel을 거쳐 `React.createElement(...)` 함수 호출로 변환된다. 태그가 값처럼 동작하는 이유, `{}` 안에 표현식만 들어가는 이유, 태그를 꼭 닫아야 하는 이유가 전부 여기서 나온다.

## 🔀 조건부 렌더링 - return 안에서 if를 못 쓰는 이유

```jsx
{/*return 안에서는 if문 사용이 불가능하다. -> 3항 연산자로 대체 가능*/}
{1 + 1 === 2 ? (<p>맞아요</p>) : (<p>틀려요</p>)}
```

`{}` 안에는 표현식만 들어갈 수 있다는 걸 알고 나니, "왜 삼항 연산자를 그렇게 자주 쓰는지"가 바로 이해됐다. `if`는 "이렇게 해라"라고 실행 흐름을 지시하는 **문(statement)**이라 값이 없고, 삼항 연산자(`조건 ? A : B`)는 그 자체로 **결과값을 반환하는 표현식**이기 때문에 `{}` 안에 들어갈 수 있는 것이었다.

그런데 조건이 3개, 4개로 늘어나면 삼항 연산자를 중첩해서 쓰기엔 가독성이 확 떨어진다. 실습 코드는 그 상황을 즉시실행함수(IIFE)로 풀었다.

```jsx
{
  (() => {
    if (age === 10) {
      return <div>열살</div>
    }
    if (age >= 20) {
      return <div>스무살</div>
    }
    if (age >= 30) {
      return <div>서른살</div>
    }
  })()
}
```

`{}` 안에 들어갈 수 있는 건 표현식뿐인데, **"함수를 정의하고 그 자리에서 바로 호출한 결과"**는 함수 호출 표현식이니 규칙을 어기지 않는다. 함수 몸통 안에서는 당연히 `if`를 자유롭게 쓸 수 있으니, 이 패턴으로 `{}` 안에서도 사실상 `if`를 쓰는 효과를 낸 것이다. 저번에 실행 컨텍스트를 정리하면서 봤던 "함수가 호출되면 자기만의 실행 컨텍스트가 생겼다가, 끝나면 사라진다"는 개념이 여기서도 그대로 적용된다 - 이 IIFE도 호출되는 즉시 실행 컨텍스트가 만들어지고, 값을 반환하자마자 스택에서 빠진다.

> ✅ **핵심**: JSX의 `{}`는 표현식만 허용한다. 조건이 단순하면 삼항 연산자, 복잡하면 즉시실행함수(IIFE)로 "함수 호출이라는 표현식" 안에 `if`를 숨겨서 쓴다.

## 🎨 스타일링 두 가지 방법 - 인라인 style vs className

```jsx
const styles = {
    fontSize : 26,
    fontWeight : 700,
    color : 'blue',
    backgroundColor: 'yellowgreen'
};

return(
    <div>
        <h1 style={{color : 'red'}}>Hello Inline Style</h1>
        <p style={styles}>Java Script Object Style</p>
        <span>Use Style Sheet</span>
        <h1 className="App-title">Use ClassName</h1>
    </div>
)
```

`style={{color : 'red'}}` 처음 봤을 때 중괄호가 두 개라서 오타인 줄 알았는데, 각자 역할이 달랐다.

- **바깥 `{ }`**: JSX 안에서 JS 값을 쓰겠다는 표시 (위에서 본 그 `{}`)
- **안쪽 `{ }`**: 그 안에 들어간 값이 **객체 리터럴**이라는 표시

즉 `style={ {color: 'red'} }`인 셈이고, `styles`처럼 변수로 미리 빼두면 `style={styles}`로 중괄호 하나만 남는다. 여기서 CSS 속성명이 `font-size`가 아니라 `fontSize`인 것도 눈에 띄었는데, JS 객체의 key는 하이픈을 쓸 수 없으니 camelCase로 바꿔 쓰는 규칙이었다.

반면 `className="App-title"`은 HTML의 `class`와 똑같은 개념으로, 외부 `.css` 파일에 정의해둔 스타일을 이름으로 연결하는 방식이다.

![인라인 style 객체와 className 두 가지 스타일링 방식 비교](/images/react/style_vs_classname.svg)

두 방식을 나란히 보고 나니 실무에서 왜 className을 기본으로 쓰라고 하는지 감이 왔다. 인라인 style은 그 요소에만 딱 붙어서 재사용이 안 되고, CSS의 캐스케이딩(우선순위) 규칙도 다 무시하고 항상 최우선으로 적용돼버린다. 값이 상황에 따라 계속 바뀌는 스타일(예: 클릭할 때마다 색이 변하는 것)이 아니라면, 유지보수와 재사용을 생각해서 className + 외부 CSS가 기본값에 가깝다는 걸 알게 됐다.

> ✅ **핵심**: `style={ {...} }`는 JS 객체를 즉석에서 넘기는 인라인 스타일(camelCase, 항상 최우선 적용)이고, `className`은 외부 CSS와 연결하는 방식(재사용 가능, 일반 CSS 우선순위 규칙 적용)이다. 기본은 className, 동적인 값만 인라인으로.

## 🤔 감이 안 왔던 부분, 다시 짚어보기

- **`{}` 안에 표현식만 된다는 규칙, 함수형 컴포넌트 자체에는 왜 안 걸리나?** → 처음엔 헷갈렸는데, `function App() { ... return (...) }`에서 함수 **몸통**은 일반 JS 코드 블록이라 `if`, `let`, 반복문 다 자유롭게 쓸 수 있다. 규칙이 걸리는 건 오직 `return`이 뱉어내는 JSX 안, `{}`로 감싼 부분뿐이었다. "함수 몸통 vs JSX 안"을 구분해서 봐야 헷갈리지 않는다는 걸 이번에 명확히 했다.
- **인라인 style이 CSS보다 항상 우선한다는 게 어느 정도인가?** → 실습에서는 다루지 않았지만, CSS 명시도(specificity) 개념까지 가면 `!important`를 제외하면 인라인 스타일이 사실상 가장 강하다고 알고 있다. 다음에 실제로 className과 style을 같은 요소에 동시에 걸어서 어떤 게 이기는지 콘솔로 직접 확인해봐야겠다.
- **Fragment(`<>`)와 `<div>`로 감싸는 것의 실질적 차이** → 이번 실습 코드에도 둘 다 나왔는데 (`<div className="App">`으로 감싼 부분 vs `<>`로 감싼 최상위), 정확히 어떤 기준으로 골라 쓰는지는 아직 감이 부족하다. "스타일링/이벤트 대상이 필요하면 div, 그냥 묶기만 하면 Fragment" 정도로 추측만 해뒀고, 다음 실습에서 CSS 레이아웃을 다룰 때 다시 확인해봐야겠다.

## 💡 정리하면

첫 React 실습에서 가장 크게 얻은 건 "JSX는 마법이 아니라 결국 함수 호출"이라는 관점이었다. 이 하나를 이해하고 나니 `{}` 규칙, Fragment, 태그를 꼭 닫아야 하는 이유가 전부 같은 줄기에서 나온다는 게 보였다.

**오늘의 핵심 4가지**

- 📚 JSX는 Babel을 거쳐 `React.createElement(...)` 함수 호출로 변환된다 - 그래서 태그를 값처럼 다룰 수 있다
- 🔀 JSX의 `{}` 안에는 표현식만 들어간다 - 조건이 단순하면 삼항 연산자, 복잡하면 IIFE로 우회
- 🎨 인라인 style은 JS 객체(camelCase, 항상 최우선), className은 외부 CSS 연결(재사용 가능, 일반 우선순위)
- 🧩 함수 몸통(자유로운 JS)과 `return` 안 JSX(표현식만 허용)를 구분해서 봐야 규칙이 헷갈리지 않는다

**다음에 확인해볼 것**

1. 같은 요소에 className과 style을 동시에 걸어서 실제로 어느 쪽이 이기는지 콘솔로 확인해보기
2. Fragment(`<>`)와 `<div>`로 감싸는 기준을 실제 레이아웃/스타일링 상황에서 비교해보기
3. `React.createElement`를 직접 호출해서 JSX 없이 같은 화면을 만들어보고 변환 과정을 눈으로 확인해보기
