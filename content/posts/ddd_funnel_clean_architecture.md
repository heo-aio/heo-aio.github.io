## 🧩 DDD: 업무 기준으로 코드 설계하기

**DDD(Domain-Driven Design, 도메인 주도 설계)**: 코드를 개발자 기준이 아니라 **실제 업무(도메인) 기준**으로 설계하자는 접근이다.

### 왜 필요할까?

DDD 없이 개발하면 보통 **DB 테이블부터 설계**한다. 그러면 `OrderService`, `OrderUtil`, `OrderManager` 같은 이름만 봐서는 뭘 하는지 모호한 클래스에 로직이 뒤섞이기 쉽다. 그러면 이런 일이 생긴다.

- 기획자가 "환불 규칙 바꿔 주세요"라고 해도 **코드 어디를 고쳐야 하는지 모른다.**
- 기획자와 개발자가 **같은 단어를 다른 뜻으로 써서** 소통 오류가 생긴다.

### 핵심 개념 4가지

**① 유비쿼터스 언어 (공통 언어)**
기획자, 디자이너, 개발자가 **같은 단어**를 쓰고, 그 단어를 **코드에도 그대로** 쓴다.
예: 기획서에 "주문 취소"라고 적혀 있으면 코드에도 `order.cancel()`이 있어야 한다.

**② 바운디드 컨텍스트 (경계)**
같은 단어도 영역마다 뜻이 다르다. 영역별로 선을 긋고 **각자 모델을 따로** 가진다.

| 영역 | "상품"이 의미하는 것 |
|---|---|
| 주문 | 가격, 수량 |
| 배송 | 무게, 크기 |

"상품" 하나에 모든 정보를 다 넣은 거대한 클래스를 만드는 대신, 주문 쪽 상품과 배송 쪽 상품을 따로 둔다.

**③ 엔티티 vs 값 객체**

| | 기준 | 예시 |
|---|---|---|
| 엔티티 | **ID**로 구별한다. 속성이 바뀌어도 같은 대상 | 회원 (이름이 같아도 다른 회원일 수 있음) |
| 값 객체 | **값 자체**가 같으면 같은 것. 한번 만들면 바꾸지 않는다(불변) | 돈 1000원 (어느 1000원이든 같음) |

**④ 애그리거트 (Aggregate)**
**함께 움직여야 하는 객체들을 하나로 묶고, 입구(루트)를 하나만** 둔다. 묶음 안의 데이터는 **루트를 통해서만** 바꾼다.
예: 주문과 주문 항목은 항상 같이 다루니까 `Order`가 루트가 된다. 주문 항목을 밖에서 직접 건드리지 않고 `order`를 통해서 바꾼다.

### 파이썬으로 보면

```python
from dataclasses import dataclass

# 값 객체: 값이 같으면 같은 것, 바꿀 수 없음(frozen)
@dataclass(frozen=True)
class Money:
    amount: int

Money(1000) == Money(1000)   # True

# 엔티티 + 애그리거트 루트: ID로 구별, 규칙은 객체 안에
class Order:
    def __init__(self, order_id, items):
        self.id = order_id
        self.items = items          # 주문 항목은 Order를 통해서만 다룸
        self.status = "결제완료"

    def cancel(self):               # 기획서의 '주문 취소' 그대로
        if self.status == "배송중":
            raise ValueError("배송 중에는 취소할 수 없습니다")
        self.status = "취소"
```

"환불/취소 규칙을 바꿔 주세요"라는 요청이 오면 `Order.cancel()`만 보면 된다. 규칙이 서비스 여기저기에 흩어져 있지 않기 때문이다.

### 언제 쓰면 좋을까?

- 효과적으로 하려면 **도메인 전문가(현업 담당자)와 적극적으로 소통**해야 한다.
- **복잡한 업무 규칙이 많은 서비스**에서 효과가 크다. 단순 CRUD 게시판에는 과하다.
- 처음부터 전부 적용하려 하지 말고 **공통 언어**와 **"규칙은 객체 안에 두기"**부터 시작해도 코드가 크게 좋아진다.

## 🔻 퍼널: 사용자가 줄어드는 흐름

**퍼널(Funnel)**은 깔때기라는 뜻이다. 서비스에 들어온 사용자가 단계를 거치면서 **점점 줄어드는 흐름**을 깔때기에 비유한 것이다.

### 왜 볼까?

**어느 단계에서 사용자가 많이 이탈하는지** 찾기 위해서다. 이탈이 많은 곳이 개선할 지점이다.

```
상품 조회 1000명 → 장바구니 200명 → 결제 시작 100명 → 결제 완료 80명
```

| 용어 | 뜻 | 예시 |
|---|---|---|
| 전환율 | 다음 단계로 **넘어간** 비율 | 장바구니 100명 → 결제 시작 50명이면 50% |
| 이탈률 | 중간에 **떠난** 비율 | 위 예시는 50% (= 100% − 전환율) |

### 마케팅 퍼널: AARRR

사용자의 전체 여정을 보는 틀이다.

| 단계 | 영문 | 질문 |
|---|---|---|
| 획득 | Acquisition | 어떻게 들어오는가 |
| 활성화 | Activation | 첫 좋은 경험을 했는가 |
| 유지 | Retention | 다시 돌아오는가 |
| 수익 | Revenue | 돈을 쓰는가 |
| 추천 | Referral | 남에게 알리는가 |

### 개발자 관점

퍼널을 보려면 **사용자 행동을 이벤트로 기록**해야 한다. 기록이 없으면 분석 자체가 안 된다.

```python
# 이벤트 기록 예시: 누가, 언제, 무엇을 했는지
track(user_id=42, event="add_to_cart", props={"product_id": 7})
track(user_id=42, event="checkout_start")
```

그래서 기획 단계에서 "어떤 행동을 이벤트로 남길지"를 같이 정해 두는 게 좋다.

## 🔁 리텐션: 다시 돌아오는 사용자

**리텐션(Retention)**은 서비스를 처음 쓴 사용자가 **시간이 지나도 계속(다시) 돌아와 쓰는 비율**이다.

- 보통 가입(또는 첫 사용) 후 **1일, 7일, 30일 뒤**에 다시 왔는지 본다. (D1, D7, D30 리텐션)
- 예: 오늘 가입한 100명 중 7일 뒤에 접속한 사람이 20명이면 D7 리텐션은 20%.
- 퍼널이 "한 번의 흐름 안에서 단계별로 줄어드는 정도"라면, 리텐션은 **시간 축으로 다시 오는 정도**다.
- 사용자를 모으는 것(획득)보다 **계속 쓰게 하는 것**이 중요하다는 이야기와도 이어진다. 특강에서 "출시보다 운영이 더 중요하다"고 했던 것과 같은 맥락이다.

## 🧅 클린 아키텍처: 핵심 로직을 바깥 기술에서 보호하기

**핵심 업무 로직이 DB, 프레임워크, 외부 API 같은 바깥 기술에 의존하지 않게** 설계하자는 구조다.
예: DB를 MySQL에서 MongoDB로 바꾸거나, FastAPI를 Django로 바꿔도 **핵심 로직은 그대로**여야 한다.

### 4개 계층 (안쪽 → 바깥쪽)

| 계층 | 역할 | 예시 |
|---|---|---|
| Entities (엔티티/도메인) | 기업 전체의 핵심 비즈니스 규칙. 특정 애플리케이션에 종속되지 않는 가장 순수한 데이터와 로직 | `Order`, `Money` |
| Use Cases (유스케이스) | 애플리케이션별 규칙과 흐름. 시스템이 **무엇을 하는지**(주문하기, 회원가입 등) 정의하고 엔티티를 조합해 실행 | `CancelOrder` |
| Interface Adapters | 안쪽(유스케이스, 엔티티)과 바깥쪽(DB, UI) 사이에서 **데이터를 변환** | 컨트롤러, 리포지토리 구현체 |
| Frameworks & Drivers | 가장 바깥쪽 세부사항 | 웹 프레임워크(Spring, Express), DB(MySQL, MongoDB), UI(React, Android) |

### 가장 중요한 규칙: 의존성은 안쪽으로만

> **의존성은 항상 바깥에서 안쪽으로만 향한다.** 안쪽 계층은 바깥쪽을 몰라야 한다.

즉 `Order` 같은 엔티티는 MySQL이나 FastAPI를 **전혀 몰라야** 한다. 이게 지켜져야 "DB를 바꿔도 핵심 로직이 그대로"가 가능하다. 그러면 유스케이스가 DB를 써야 할 때는 어떻게 할까? **인터페이스(추상)**에만 의존하고, 실제 구현은 바깥에서 끼워 넣는다.

### 파이썬으로 보면

```python
# [유스케이스] 인터페이스(저장소)에만 의존. MySQL인지 Mongo인지 모른다
class CancelOrder:
    def __init__(self, repo):
        self.repo = repo

    def execute(self, order_id):
        order = self.repo.find(order_id)   # 엔티티 꺼내서
        order.cancel()                     # 엔티티의 규칙 실행
        self.repo.save(order)

# [어댑터] 바깥 기술 구현. 갈아 끼우는 부분
class MySQLOrderRepository:
    def find(self, order_id): ...
    def save(self, order): ...

class MongoOrderRepository:
    def find(self, order_id): ...
    def save(self, order): ...

# [프레임워크] FastAPI는 요청을 받아 유스케이스를 호출만 한다
@app.post("/orders/{order_id}/cancel")
def cancel(order_id: int):
    CancelOrder(MySQLOrderRepository()).execute(order_id)
```

DB를 바꾸고 싶으면 `MySQLOrderRepository` → `MongoOrderRepository`로 **끼우는 부분만** 바꾸면 된다. `CancelOrder`와 `Order`는 손대지 않는다.

## 🔗 세 개념이 이어지는 지점

- **DDD**의 엔티티·값 객체가 **클린 아키텍처**의 가장 안쪽 계층(Entities)에 들어간다.
- 클린 아키텍처는 그 도메인 로직을 **바깥 기술로부터 지키는 구조**다.
- **퍼널/리텐션**은 만든 서비스를 **데이터로 검증**하는 쪽이다. 이벤트를 어떻게 남길지는 개발 설계와 연결된다.
- 특강에서 말한 "가설을 빨리 검증하자"는 흐름과도 이어진다. 만들고, 이벤트로 측정하고, 퍼널과 리텐션으로 확인한다.

## 🛠️ 헷갈렸던 부분

**1) DDD의 엔티티와 클린 아키텍처의 Entities는 같은 건가?**
→ 비슷한 생각이지만 용어가 겹치는 다른 개념이다. DDD의 엔티티는 "ID로 구별하는 객체"이고, 클린 아키텍처의 Entities는 "가장 안쪽의 핵심 규칙 계층"이다. 보통 DDD로 만든 도메인 객체를 이 계층에 둔다.

**2) 이탈률과 리텐션은 같은 말 아닌가?**
→ 다르다. 이탈률은 퍼널에서 **한 단계를 넘지 못한 비율**이고, 리텐션은 **시간이 지나도 다시 오는 비율**이다.

**3) 작은 프로젝트에도 클린 아키텍처를 써야 하나?**
→ 단순 CRUD라면 과할 수 있다. 계층을 나누는 만큼 파일과 코드가 늘어난다. 업무 규칙이 복잡해지거나 DB·프레임워크를 바꿀 가능성이 있을 때 효과가 크다.

## 💡 정리하면

| 개념 | 한 줄 요약 |
|---|---|
| DDD | 코드를 개발자 기준이 아닌 **업무(도메인) 기준**으로 설계 |
| 유비쿼터스 언어 | 기획서의 단어를 코드에도 그대로 (`주문 취소` → `order.cancel()`) |
| 바운디드 컨텍스트 | 영역마다 같은 단어의 뜻이 다르니 경계를 긋고 모델을 따로 |
| 엔티티 / 값 객체 | ID로 구별 / 값이 같으면 같음(불변) |
| 애그리거트 | 함께 움직이는 객체 묶음, 입구(루트)는 하나 |
| 퍼널 | 단계별로 줄어드는 흐름, 이탈 지점을 찾는 도구 |
| 리텐션 | 시간이 지나도 다시 오는 사용자 비율 |
| 클린 아키텍처 | 핵심 로직이 바깥 기술에 의존하지 않게. **의존성은 안쪽으로만** |

- DDD는 **업무 규칙이 복잡할 때**, 단순 CRUD에는 과하다. 처음엔 **공통 언어**와 **규칙은 객체 안에**만 해도 충분하다.
- 퍼널과 리텐션을 보려면 **사용자 행동을 이벤트로 기록**해야 한다.
- 클린 아키텍처의 핵심은 계층 이름이 아니라 **"바깥 기술을 갈아 끼워도 핵심 로직은 안 바뀐다"**는 점이다.
