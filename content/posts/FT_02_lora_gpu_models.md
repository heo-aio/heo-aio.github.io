## 🧱 Full Fine-tuning: 전체를 바꾼다

**모든 파라미터가 학습 대상**이다. 표현력은 최대지만 메모리·저장도 최대다.

- 학습 중에는 **가중치 + 기울기 + optimizer 상태**를 전부 들고 있어야 한다.
- Adam 기준 대략 추정: fp32 가중치 4 + fp32 기울기 4 + Adam 상태(모멘텀·분산) 8 = **파라미터당 약 16바이트**. (활성값·임시 버퍼는 별도)
- 산술 추정: 7B ≈ 112GB, 0.5B ≈ 8GB. 이름의 B와 실제 파라미터 수는 다르다(Qwen2.5-7B는 7.61B → 약 122GB).
- 분산 학습·오프로딩·8bit optimizer를 안 쓰면 80GB급 GPU 한 장으로도 7B Full FT는 어렵다. 그래서 **소형 모델 위주**다.
- 결과물은 **전체 가중치 사본**이다. 예: 1.5B 모델을 16bit로 저장하면 약 3GB.

## 🧩 PEFT / LoRA: 일부만 바꾼다

**PEFT(Parameter-Efficient Fine-Tuning)**: 본체를 **동결**하고 **작은 파라미터만 학습**해서 학습 메모리를 줄이는 방식이다.

- 본체 파라미터를 얼리면 기울기·optimizer 상태는 **학습하는 파라미터 분량만** 필요하다.
- 하지만 **본체 가중치와 활성값 메모리는 그대로 필요**하다. (이게 퀴즈 포인트)

| 대표 기법 | 아이디어 |
|---|---|
| LoRA | 층마다 저랭크 행렬(어댑터)을 붙여 그것만 학습 |
| QLoRA | 본체를 4bit로 올리고 + LoRA |
| Prompt/Prefix tuning | 학습 가능한 가상 토큰 |
| IA3 | 활성값 스케일 벡터 |

- 결과물은 **어댑터 파일**이다. 크기는 r, target_modules, 모델 크기에 따라 다르다(수업 실측 예: 1.5B 모델에서 q·v, r=8이면 약 4.4MB).
- 품질은 원 논문 실험에서 Full FT와 비슷한 결과가 보고됐지만, 과제에 따라 덜 배운다는 결과도 있다. 자기 데이터로 검증해야 한다.

## ⚖️ Full FT vs PEFT 비교

| | Full FT | PEFT (LoRA / QLoRA) |
|---|---|---|
| 학습 파라미터 | 전체 | 일부·추가 파라미터 |
| 학습 메모리 | 가중치+기울기+optimizer 전체 (파라미터당 약 16바이트) | 기울기·optimizer는 학습 파라미터 분량만. 본체 가중치·활성값은 여전히 필요 |
| 같은 VRAM에서 다룰 크기 | 작음 | 더 큼 (QLoRA 원 논문: 65B를 48GB GPU 한 장에서) |
| 산출물 | 전체 가중치 사본 | 어댑터 파일 |
| 여러 과제 | 과제마다 모델 사본 | 본체 1개 + 과제별 어댑터 |
| 기존 과제 성능 유지(망각) | LoRA보다 저하가 큰 경향 | 더 유지하는 경향 (단, 목표 과제 향상은 작은 편. 코드·수학 실험의 관찰이고 모든 PEFT에 보장은 아님) |
| 과적합 | 두 방식 모두 발생 가능. 기법 우열이 아니라 훈련·검증 loss 차이로 점검 | |

## 📝 퀴즈 ② LoRA 메모리

> LoRA가 Full Fine-tuning보다 학습 메모리를 줄여주는 이유로 가장 적절한 것은?

**답: 본체를 얼리고, 기울기와 optimizer 상태를 어댑터 파라미터에 대해서만 유지하기 때문.**

- Full FT는 모든 파라미터의 기울기와 optimizer 상태가 필요하다.
- LoRA는 어댑터만 학습하니 이 부분이 **크게 줄어든다.**
- 그렇다고 메모리가 어댑터 크기만큼만 드는 건 아니다. **본체 가중치와 활성값 메모리는 그대로** 필요하다. "LoRA면 모델 크기와 상관없이 가볍다"는 보기는 틀린 설명이다.

## 💾 VRAM은 뭘로 채워질까

| 추론 시 메모리 | Full FT 시 메모리 |
|---|---|
| 가중치: 파라미터 × 정밀도 바이트 | 가중치 + 기울기 + optimizer 상태 |
| KV cache + 활성값 | 학습 중 보관하는 활성값 |
| 할당기 여유 공간 + 임시 버퍼 | 할당기 여유 공간 + 임시 버퍼 |

- 4bit 양자화 후에도 비양자화 부분·메타데이터는 남는다.
- gradient checkpointing은 활성값 메모리를 줄여준다.
- **VRAM 용량이 모델·기법 선택의 첫 제약**이다. 속도는 SM·대역폭·커널·호스트에 의존해서 VRAM만으로 예측할 수 없다.

GPU 확보 방법은 크게 로컬(소비자용 24GB급 등, 초기 투자와 VRAM 상한), 클라우드 온디맨드(A100·H100 등, 시간당 과금), 공유·분할(MIG 슬라이스처럼 한 장을 나눔)이 있다. 실제 사용량은 `nvidia-smi`, `torch.cuda`로 확인한다.

## 🧭 Closed vs Open 모델

| 기준 | Closed (API) | Open (가중치 공개) |
|---|---|---|
| 가중치 접근 | 불가 | 다운로드·수정 가능 |
| 데이터 처리 경로 | 외부 전송 (전송·로그 정책 확인 필요) | 자체 운영 시 경로 통제 가능 |
| 파인튜닝 | 제공사 방식에 한정 | 자유 (Full / LoRA / QLoRA) |
| 비용 구조 | 토큰당 과금 | GPU 고정비 + 운영 |
| 라이선스 | 이용 약관 | 모델별 상이 (Apache-2.0, MIT, Llama, Gemma 등) |

주의: **가중치 공개(open weights)와 오픈소스는 구분**된다. 다운로드가 된다고 OSI 정의를 다 충족했다고 볼 수 없다. 또 공개 여부만으로 성능 우열을 판단할 수도 없다.

직접 파인튜닝하면 **얻는 것**은 데이터 통제권, 목적에 맞는 수정, 운영 선택권이고, **치르는 것**은 GPU 확보, 운영 인력, 평가 책임이다. 비용은 조건부라서 트래픽이 크면 토큰당 과금보다 자체 GPU 고정비가 저렴해지는 손익분기가 있을 수 있다.

## 🗺️ 오픈소스 LLM 생태계

**Hugging Face Hub**가 가중치·데이터셋·토크나이저를 내려받는 중심 허브다. 도구는 목적별로 나뉜다.

| 역할 | 예시 |
|---|---|
| 모델 | Qwen, Llama, Gemma, DeepSeek, EXAONE, HyperCLOVAX |
| 학습 라이브러리 | transformers, peft, trl, bitsandbytes, accelerate |
| 서빙 | vLLM, Ollama |

학습(transformers·peft·trl 등)과 배포(vLLM·Ollama)는 **다른 도구**다. 한국어 모델로는 EXAONE(LG), HyperCLOVAX-SEED(네이버)가 있고 라이선스 조건 확인이 필요하다.

## ✅ 모델 선택 체크리스트

핵심 원칙은 **범용 최고 성능보다 "목적 과제에서 충분한 가장 작은 모델"**이다.

| 확인 항목 | 질문 |
|---|---|
| 크기 | 보유 GPU의 VRAM 안에서 학습 가능한가 |
| 라이선스 | 상업 이용·재배포가 가능한가 |
| 접근성 | 승인 없이 바로 받을 수 있는가 (게이트 모델은 즉시 배포가 어려움) |
| 언어 | 한국어를 지원하는가 (카드 문구와 실제 출력을 따로 확인) |
| 계열 통일 | 같은 계열로 맞출 수 있는가 |
| chat template | 대화 형식이 정해져 있는가 (학습·추론에 동일 적용) |
| 저비용·특화 | 더 작은 모델로 충분한가 (평가로 확인) |

## 🚀 학습 후 서빙: vLLM

서빙은 학습된 모델을 API로 띄워 **동시 요청을 처리**하는 것이다. 학습과는 다른 도구가 필요하다.

- **KV cache**: 앞 토큰 계산 결과를 재사용한다. 생성 속도의 핵심이자 메모리 소비의 주범이다.
- **vLLM의 PagedAttention**: KV cache를 페이지 단위로 관리해서 동시 처리량을 높인다.
- `vllm serve <모델>` 한 줄로 OpenAI 호환 API가 뜨고, LoRA 어댑터 서빙도 지원한다(본체 1개에 어댑터 여러 개).
- 배포 시에는 처리량(throughput)과 지연(latency)이 비용을 결정한다.

## 🛠️ 헷갈렸던 부분

**1) 모델 이름의 7B면 정확히 70억 개인가?**
→ 규모 표기일 뿐이다. 실제 파라미터 수는 모델 카드로 확인한다(예: Qwen2.5-7B는 7.61B).

**2) LoRA 쓰면 7B도 GPU 한 장에서 되나?**
→ 기울기·optimizer 부담은 크게 줄지만 본체 가중치와 활성값은 올려야 해서, 모델 크기와 정밀도(4bit 등)에 따라 달라진다. 직접 VRAM 사용량을 재봐야 한다.

**3) 오픈 모델이 항상 이득인가?**
→ 아니다. 통제권은 얻지만 GPU·인력·평가 책임을 직접 진다. 트래픽이 적으면 API가 더 쌀 수 있다.

## 💡 정리하면

| 개념 | 한 줄 요약 |
|---|---|
| Full FT | 전부 학습. 메모리 최대(파라미터당 약 16바이트 추정), 산출물은 전체 사본 |
| PEFT/LoRA | 본체 동결 + 어댑터만 학습. 기울기·optimizer 메모리 절감 |
| QLoRA | 4bit 본체 + LoRA |
| VRAM | 가중치 + (학습 시) 기울기·optimizer + 활성값 + 버퍼 |
| open weights ≠ 오픈소스 | 라이선스는 모델별로 확인 |
| vLLM | PagedAttention으로 KV cache를 관리하는 서빙 도구 |

- LoRA가 줄이는 것은 **기울기와 optimizer 상태**이고, 본체 가중치·활성값은 그대로 든다.
- 모델은 **목적 과제에서 충분한 가장 작은 것**부터 검증한다.
- 다음 글에서는 "그래서 언제 파인튜닝을 해야 하나"를 정리한다.
