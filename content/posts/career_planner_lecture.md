## 🧑‍💼 기획자로서 느낀 점

강연자분이 꼽은 기획자의 모습은 이랬다.

1. 직원이지만 CEO나 임원과 **가깝게 일하는** 직원이다.
2. 잘해도, 못해도 욕먹을 때가 있다.
3. **책임은 있지만 권한이 없다.** 그래서 쉬운 길이 없다.
4. 월급 받고 배우는 **창업 사관학교**다.
5. 내가 세운 가설은 보통 안 맞는다. 그래서 **빠른 실행**이 중요하다.
6. 게임·서비스를 출시하기 전에 **고객 가설을 검증**하는 것이 가장 현명하다.
7. 제품도 중요하지만 **마케팅이 더 중요**하다. 출시보다 **운영**이 더 중요하다.
8. 창의적인 것보다 중요한 건 **문제 단 하나를 뾰족하게 해결**하는 것이다.

"내 가설은 보통 안 맞는다"가 가장 와닿았다. 개발 프로젝트를 할 때도 일단 만들어 놓고 나서 "이게 정말 필요했나?" 싶은 적이 있어서 공감이 갔다.

## 🤖 AI를 업무에 쓰는 방식

실제 업무에서 AI를 활용하는 사례도 소개해 주셨다.

| 업무 | 활용 방식 |
|---|---|
| 협업 툴 정리 | Claude Cowork로 지라·슬랙·노션 등에 흩어진 업무 히스토리를 정리하고 알림 |
| 기획문서 작성 | AI로 업무 요구사항을 정의하고 HTML 목업을 만든 뒤 Figma 파일로 전환 |
| 번역 자동화 | 패치노트 크롤링 → AI 번역 → 등록까지 자동화 |
| 디자인·개발 | C레벨을 설득하기 위한 디자인 시안 작업, 협업 툴 제작과 프론트·백엔드 코드 일부 작업 |

기획자가 디자인 시안과 개발 코드까지 직접 만진다는 점이 인상 깊었다.

## 🛠️ 빌더(Builder)라는 개념

> 기획, 디자인, 개발 직무의 경계 없이 **문제를 정의하고 해결하는 사람**

- 특정 직무 하나만 정해서는 이제 **경쟁력이 약해질 수 있다.**
- AI라는 도구로 **문제를 정의하고, 어떻게 해결할지 생각할 줄 아는 사람**이 되자는 이야기였다.
- 결국 **문제를 잘 정의하는 사람**이 필요하다.

## 🎯 문제를 잘 정의한다는 것

강연자분이 말한 요소는 네 가지였다.

| 요소 | |
|---|---|
| 전문성 | |
| 좋은 태도 | |
| 빠른 실행 | |
| 수익성 | |

그리고 일하는 환경에 대해서는 이렇게 말씀하셨다.

- 내가 **좋아하는 영역**에서
- **좋은 태도**를 가진 사람들과
- **실패에 예민하지 않은 곳**에서 일해 보자

문제 정의 예시로는 사전예약 이벤트를 들어 주셨다. 사전예약 이벤트의 메인 화면을 뿌릴 때, 이름·번호·동의사항 입력이 메인에 **잘 박혀 있는지**처럼 서비스가 실제로 잘 되기 위한 포인트를 따져 보는 것이 문제 정의라는 맥락이었다.

## 📁 신입은 무엇으로 어필할까 (포트폴리오)

질문: **신입 기획자는 어떤 걸로 어필할 수 있나요?**

- **런칭을 해 보고 그 경험을 만들어라.** 운영도 해 보고, 내가 경험한 걸 가지고 회사를 설득해 보는 식으로 면접에서 어필한다.
- 포트폴리오에 프로젝트를 나열하면 **뭘 봐야 할지 모른다.**

포트폴리오 방향은 세 가지로 정리됐다.

1. **프로젝트 하나만** 잡고 내가 어떻게 일했는지 보여주자 (버티컬하게)
2. **보고서처럼** 만들자
3. 레퍼런스는 많으니 **많이 보는 걸 추천**

나도 프로젝트를 여러 개 나열하기보다 하나를 깊게 파는 쪽이 낫겠다고 느꼈다.

## 💬 Q&A에서 기억에 남은 것

**Q. 문제 정의와 가설 검증에 AI를 어떻게 활용하나요?**
A. 경험이 중요해서 AI를 직접 활용하지는 않는 것 같다. 참고할 레퍼런스를 AI로 찾아서 장점만 가져온다.

**Q. 클로드와 제미나이를 함께 쓴다면 어떻게 쓰시나요?** (역할을 나눠서 쓰려고 하면 뜻대로 안 되더라는 질문)
A. 토큰을 써서 제대로 만들어야 하는 작업은 **Claude**, 잔바리 업무는 **Gemini**로 쓴다.

**Q. AI 때문에 "기획은 누구나 할 수 있다"는 인식이 있는데, 기획 직무의 전문성은?**
- 앞서 말씀하신 **"기획은 책임을 지는 일"**이라는 표현이 인상 깊었다는 질문이었다.
- 질문자는 좋은 기획의 출발점이 **경험의 질**이라고 보고, 판단력을 위해 경험을 어떻게 축적하고 정제하시는지 물었다.
- 답변: **고집을 가지지 않으려고 노력**한다. 업계에 관심이 아주 많아야 하고, "내가 생각하는 가설이 진짜 맞을까?"를 계속 의심한다.

**그 밖에 해 주신 말씀**
- 게임 개발자들도 보안 같은 중요한 부분은 **손코딩**하고, 나머지는 거의 **바이브코딩**을 한다.
- LLM이 완벽하지 않으니 **생각하는 게 중요**하다.
- 실패에 예민한 회사에 있으면 성장이 힘들 수 있다.
- 영원히 잘 나가는 회사도, 영원히 못 나가는 회사도 없다. 인생은 어떻게 될지 모르니, 하고 싶은 걸 다 하면서 열심히 하다 보면 기회가 온다.

## 🛠️ 헷갈렸던 부분

**1) '빌더'는 기획·디자인·개발을 다 잘해야 한다는 뜻인가?**
→ 메모 기준으로는 전부 전문가가 되라는 말이 아니라, **직무 경계에 갇히지 않고 문제를 정의하고 해결하는 사람**이라는 뜻으로 이해했다. AI가 그 경계를 낮춰 주는 도구다.

**2) AI를 쓰면 문제 정의도 AI가 해 주나?**
→ 아니다. 강연자분은 문제 정의는 경험으로 하고, AI는 레퍼런스를 찾는 데 쓴다고 했다. **생각은 내가 한다.**

## 💡 정리하면

| 키워드 | 한 줄 요약 |
|---|---|
| 가설 | 내 가설은 보통 안 맞는다 → 빠른 실행, 출시 전 고객 가설 검증 |
| 운영 | 출시보다 운영, 제품보다 마케팅이 더 중요할 수 있다 |
| 빌더 | 직무 경계 없이 문제를 정의하고 해결하는 사람 |
| 문제 정의 | 전문성, 좋은 태도, 빠른 실행, 수익성 |
| 포트폴리오 | 프로젝트 하나를 버티컬하게, 보고서처럼, 런칭·운영 경험 중심 |
| AI 활용 | 잔바리는 가볍게, 제대로 만들 건 토큰을 써서. 그래도 생각은 내가 |

- AI가 도구가 될수록 **무엇을 만들지, 왜 만드는지 정의하는 힘**이 중요해진다는 이야기였다.
- 나는 개발 쪽이지만 "개발만 잘하면 된다"에서 한 걸음 더 나아가 **문제를 정의하는 연습**도 같이 해야겠다고 느꼈다.
- 포트폴리오는 여러 개를 나열하기보다 **하나를 끝까지 운영해 본 경험**으로 만들자.
