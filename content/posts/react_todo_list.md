## 🔗 자식이 부모의 state를 바꾸는 방법 - 함수를 Props로 내려주기

```jsx
// App.jsx
// 데이터는 부모에서 자식으로 흐르지
// 자식에서 부모로 흐를 수 없다.
let [work, setWork] = useState("");
let [list, setList] = useState([]);
```

이 주석을 보자마자 2편에서 정리하다가 남겨뒀던 질문이 떠올랐다 - "Props로 받은 값을 자식이 바꾸고 싶을 땐 실무에서 어떻게 하지?" 그 답이 이번 실습에 그대로 있었다.

```jsx
// App.jsx
<Input input_work = {input_work} work = {work} onInsert = {onInsert}/>

// input.jsx
function Input(props) {
    let {input_work, work, onInsert} = props;
    return (
        <div>
            <input type={"text"} value={work} onChange={input_work} onKeyUp={send}/>
            <button onClick={onInsert}>추 가</button>
        </div>
    )
}
```

`Input` 컴포넌트 안에는 `useState`가 단 하나도 없다. `work`라는 값도, 그 값을 바꾸는 `input_work`라는 **함수**도 전부 부모(`App`)가 만들어서 Props로 내려준 것들이다. `Input`은 사용자가 타이핑하거나 버튼을 누르면 그냥 **받은 함수를 실행**할 뿐이다.

![부모가 함수를 Props로 내려주고, 자식은 값을 직접 바꾸는 대신 그 함수를 호출해서 부모에게 변경을 요청하는 흐름](/images/react/lifting_state_up.svg)

정리하면 이런 흐름이다.

1. 부모(`App`)가 `input_work`, `onInsert` 같은 함수를 만든다
2. 그 함수를 Props로 자식(`Input`)에게 내려준다
3. 자식은 이벤트(입력, 클릭)가 발생하면 **그 함수를 호출**한다
4. 함수 안에서 `setWork(...)`, `setList(...)`가 실행되면서 진짜 state가 바뀌고, 부모가 리렌더링된다

자식이 state를 "직접" 바꾸는 게 아니라, **"바꿔줘"라는 요청을 함수 호출로 부모에게 보내는 것**이었다. 이걸 "state를 끌어올린다(lifting state up)"고 부른다는 것도 이번에 찾아보고 알았다 - 여러 컴포넌트가 같은 데이터를 공유해야 하면, 그 데이터를 가장 가까운 공통 부모에 두고 자식들에게는 값과 그 값을 바꾸는 함수를 같이 내려주는 패턴이었다.

> ✅ **핵심**: 자식은 부모의 state를 직접 바꿀 수 없다. 대신 부모가 state를 바꾸는 함수 자체를 Props로 내려주면, 자식은 그 함수를 호출해서 "변경 요청"을 부모에게 전달한다.

## ⌨️ Enter 키 감지하기 - keyCode

```jsx
const send = function(e){
    console.log(e);
    if (e.keyCode == 13) {
        onInsert();
    }
}

<input onKeyUp={send} />
```

버튼을 안 누르고 Enter만 쳐도 추가가 되길래 신기했는데, `onKeyUp` 이벤트로 들어오는 이벤트 객체(`e`)에 `keyCode`라는 값이 있고, Enter 키의 코드가 `13`이라는 걸 이번에 알았다. 눌린 키가 13(Enter)일 때만 `onInsert()`를 호출하는 식으로 조건을 건 것이다. `onClick={onInsert}`와 `onKeyUp={send}`(내부에서 조건부로 `onInsert()` 호출) 두 가지 경로가 결국 같은 함수로 합쳐지는 구조를 보면서, "버튼 클릭"과 "Enter 입력"이 그냥 같은 동작을 부르는 두 개의 다른 트리거였다는 게 정리됐다.

> ✅ **핵심**: 키보드 이벤트의 `e.keyCode`로 어떤 키가 눌렸는지 알 수 있다. Enter는 13. 버튼 클릭과 Enter 입력 모두 결국 같은 핸들러 함수를 호출하도록 연결하면 된다.

## 🔢 id 자동 증가에 useRef를 쓴 이유 - 주석에 남은 실패담

이 부분이 오늘 실습에서 제일 오래 붙잡고 있었던 곳이다. 새 할 일을 추가할 때마다 고유한 `id`가 필요한데, 코드에 이런 주석이 남아 있었다.

```jsx
// let idx = 3; // 함수 안에 있으면 onInsert호출 될 때 마다 3으로 초기화되니 밖으로
// -> 근데 리랜더링될 때 마다 다시 3으로 됨 문제있음

// React에서 "값이 변해도 리렌더링을 일으키지 않으면서(렌더링과 무관한 값),
// 값을 계속 유지하고 싶은 경우"에 사용하는 도구가 useRef
const idx = useRef(4);
```

이 주석이 실패 과정을 그대로 보여줘서 오히려 이해가 빨랐다.

- **시도 1**: `onInsert` 함수 **안에** `let idx = 3`을 두면, 함수가 호출될 때마다 그 줄이 다시 실행되면서 매번 3으로 리셋된다. 당연히 실패.
- **시도 2**: 그럼 `onInsert` 함수 밖, `App` 컴포넌트 몸통에 `let idx = 3`을 두면? `App` 컴포넌트 자체가 `setList`가 호출될 때마다 **처음부터 다시 실행**되는 함수이기 때문에, 리렌더링될 때마다 이 줄도 다시 실행되면서 또 3으로 리셋된다. 여전히 실패.
- **해결**: `useRef(4)`로 만들면, `idx.current`는 컴포넌트가 몇 번을 리렌더링되든 **그 객체 자체가 유지**된다. 3편에서 정리했던 "useRef는 리렌더링과 무관하게 값을 계속 붙잡고 있다"는 그 특성이 여기서 정확히 필요했던 것이다.

`onInsert` 안에서 `idx.current += 1`로 증가시키는데, 이걸 `setState`로 했다면 상태가 바뀔 때마다 불필요한 리렌더링이 한 번 더 일어났을 거다. 화면에 `idx` 값 자체를 보여줄 일은 없으니(그냥 내부적으로 다음 id를 계산하는 용도), state가 아니라 ref가 정확히 맞는 선택이었다는 것도 이해됐다.

> ✅ **핵심**: 일반 변수는 함수 안이든 컴포넌트 몸통이든 호출/리렌더링마다 다시 초기화된다. "화면엔 안 보이지만 값은 계속 유지해야 하는" 경우(예: 자동 증가하는 id)엔 `useRef`가 정확한 도구다.

## 📋 리스트 렌더링 - map과 key

```jsx
let items = todos.map(function(todo){
    return (
        <div key={todo.id} className={"item"}>
            ...
        </div>
    )
});

return(<div>{items}</div>)
```

배열(`todos`)을 화면에 그리려면 배열 자체를 JSX에 넣을 수 없으니, `map`으로 각 항목을 JSX 태그로 **변환한 새 배열**을 만들어서 그 배열을 렌더링한다는 걸 확인했다. 여기서 `key={todo.id}`를 빼먹으면 콘솔에 경고가 뜨는데, 왜 필요한지 찾아보니 React가 리스트의 각 항목을 구분해서 "어떤 게 추가/삭제/순서변경 됐는지" 효율적으로 파악하기 위한 식별자라고 한다. `id`처럼 각 항목마다 고유하고 변하지 않는 값을 쓰는 게 맞고, 배열의 인덱스를 key로 쓰면 항목이 삭제되거나 순서가 바뀔 때 엉뚱한 항목이 다시 그려지는 문제가 생길 수 있다고 하니, 지금 `todo.id`를 쓴 게 정석이었던 셈이다.

> ✅ **핵심**: 배열을 화면에 그리려면 `map`으로 JSX 배열로 변환해야 한다. 각 항목에는 고유하고 안정적인 `key`가 필요하며, 인덱스보다는 데이터 자체의 id를 쓰는 게 안전하다.

## ☑️ 체크박스에서 "어떤 항목인지" 알아내는 두 가지 방법

같은 목적(어떤 항목이 이벤트를 발생시켰는지 알아내기)을 `onToggle`과 `onDelete`가 서로 다른 방식으로 풀고 있어서 비교해봤다.

```jsx
// List.jsx - onToggle: 클로저로 id를 직접 넘김
<input onChange={function(e){onToggle(e, todo.id)}}/>

// App.jsx
const onToggle = function(e, id){
    let index = list.findIndex(function(item){ return item.id === id; });
    ...
}
```

```jsx
// List.jsx - onDelete: 그냥 함수 자체를 넘김
<div id={todo.id} className={"delete"} onClick={onDelete}>[삭제]</div>

// App.jsx
const onDelete = function(e){
    const id = e.target.id; // DOM 요소에 심어둔 id 속성을 이벤트 객체에서 읽음
    let index = list.findIndex(function(item){
        return item.id === parseInt(id);
    });
    ...
}
```

- **`onToggle` 방식**: `map` 반복문 안에서 `todo.id`를 이미 알고 있으니, 화살표/익명 함수로 한 번 감싸서 `onToggle(e, todo.id)`처럼 **직접 인자로 넘긴다.** (클로저가 각 반복마다의 `todo.id`를 기억해준다.)
- **`onDelete` 방식**: 함수를 감싸지 않고 `onClick={onDelete}`로 그냥 넘긴 다음, 그 태그에 미리 심어둔 `id={todo.id}` 속성을 이벤트 객체의 `e.target.id`로 **꺼내서** 사용한다.

두 방식 다 결과적으로 "몇 번 항목인지"를 알아내는 게 목적인데, 접근이 다르다는 걸 비교하고서야 감이 왔다. `e.target.id`로 읽는 방식은 HTML 속성이라 값이 항상 **문자열**로 나온다는 것도 알게 됐다 - 그래서 `onDelete`에서 `item.id === parseInt(id)`처럼 숫자로 변환해서 비교하고 있었다 (반면 `onToggle`은 `todo.id`를 JS 값 그대로 넘겨받아서 `===`로 바로 비교해도 문제없다).

> ✅ **핵심**: 반복문 안에서 특정 항목의 식별자가 필요할 때는 (1) 클로저로 감싸서 직접 인자로 넘기거나, (2) DOM 속성에 심어두고 `e.target`에서 읽는 두 가지 방법이 있다. DOM에서 읽은 값은 항상 문자열이라 비교 시 타입 변환이 필요할 수 있다.

## ⚠️ 발견한 함정 - 얕은 복사(shallow copy)

정리하다가 코드를 다시 읽어보니 눈에 걸리는 부분이 있었다.

```jsx
const onToggle = function(e, id){
    let index = list.findIndex(function(item){ return item.id === id; });
    let new_arr = [...list];              // 배열 복사
    new_arr[index].done = !list[index].done;  // 그 안의 객체를 직접 수정
    setList(new_arr);
}
```

`[...list]`로 새 배열을 만드는 건 맞는데, `new_arr[index]`가 가리키는 건 사실 **원본 `list[index]`와 완전히 같은 객체**다. 스프레드 연산자(`...`)는 배열이라는 "상자"만 새로 복사하고, 그 안에 들어있는 객체는 참조(주소)만 복사하기 때문이다. 그래서 `new_arr[index].done = ...`으로 값을 바꾸면, 사실은 **원본 `list` 안의 객체까지 같이 바뀌어 버린다.**

![스프레드 연산자로 배열은 복사되지만, 배열 안의 객체는 원본과 여전히 같은 참조를 공유해서 하나를 수정하면 둘 다 바뀌는 문제](/images/react/shallow_copy_pitfall.svg)

당장은 `setList(new_arr)`로 배열 자체는 새 참조가 되니까 화면이 잘 갱신돼서 문제가 안 보인다. 하지만 "state는 직접 건드리면 안 되고 항상 새로운 값으로 통째로 교체해야 한다"는 원칙(불변성, immutability)을 생각하면, 지금 방식은 사실 원본 `list`를 몰래 변형(mutate)하고 있는 것이다. 나중에 이전 상태와 비교하는 로직이 추가되거나 `React.memo` 같은 최적화를 쓰게 되면 이 부분에서 예상 못한 버그가 날 수 있다고 한다.

**더 안전한 방식**은 이렇게 객체 자체도 새로 만드는 것이다.

```jsx
let new_arr = list.map(function(item){
    return item.id === id ? {...item, done: !item.done} : item;
});
setList(new_arr);
```

이렇게 하면 바뀐 항목만 새 객체로 교체하고, 나머지 항목은 원래 참조를 그대로 재사용한다. 지금 당장 실습에서 버그가 눈에 띄진 않았지만, "왜 이렇게 짜야 하는지" 이유를 알아두면 나중에 비슷한 코드를 볼 때 바로 알아챌 수 있을 것 같다.

> ✅ **핵심**: `[...배열]`은 배열만 새로 복사하고, 안에 들어있는 객체는 원본과 참조를 공유한다. 배열 안의 객체까지 안전하게 바꾸려면 그 객체도 `{...객체, 바뀐값}`처럼 새로 만들어야 진짜 불변성이 지켜진다.

## 🤔 감이 안 왔던 부분, 다시 짚어보기

- **`onDelete`에 있는 `new_arr[index].done = !list[index].done;` 이 줄, 왜 있는 거지?** → 삭제하기 직전에 `done` 값을 반전시키고 나서 `splice`로 지우는데, 어차피 지울 항목이면 이 줄이 굳이 필요한가 싶다. `onToggle` 코드를 복사해서 만들다가 지우는 걸 깜빡한 줄일 가능성이 높아 보이는데, 다음 실습 때 이 줄을 지워도 정말 동작에 차이가 없는지 직접 확인해봐야겠다.
- **`splice`로 배열을 지우는 게 스프레드 방식(`filter`)보다 나은가?** → `new_arr.splice(index, 1)`는 이미 복사된 `new_arr`를 그 자리에서 직접 수정(mutate)하는 방식이다. 복사본이니까 원본을 해치진 않지만, `list.filter(item => item.id !== id)`처럼 아예 "지울 항목을 뺀 새 배열"을 만드는 방식이 더 일관되게 불변성을 지키는 방법 같다. 다음에 두 방식을 실제로 바꿔서 동작 차이가 있는지 비교해봐야겠다.
- **`useEffect(fn, [])`로 넣은 초기 데이터, 실무에서는 보통 여기서 서버 API를 부르나?** → 지금은 하드코딩된 배열을 `setList`로 넣었는데, 패턴 자체는 "컴포넌트가 처음 뜰 때 데이터를 가져온다"는 게 API 호출과 완전히 같은 모양이다. 다음에 fetch나 axios를 배우면 이 자리에 그대로 API 호출을 넣어보는 실습을 해봐야겠다.

## 💡 정리하면

이번 실습이 유독 어려웠던 건 새로운 개념이 나와서가 아니라, **지금까지 따로 배운 개념들을 한 화면 안에서 동시에 조합**해야 했기 때문이었다. 되짚어보니 각 조각은 이미 배운 것들이었다 - Props로 함수 내려주기(2편), useRef로 리렌더링 없이 값 유지하기(3편), useEffect로 초기 데이터 세팅하기(4편). 이번 실습은 그 조각들을 "실제로 동작하는 앱"으로 조립해보는 첫 경험이었던 셈이다.

**오늘의 핵심 6가지**

- 🔗 자식은 부모의 함수를 Props로 받아 호출하는 방식으로 부모의 state를 간접적으로 바꾼다 (lifting state up)
- ⌨️ `e.keyCode === 13`으로 Enter 키를 감지해서 버튼 클릭과 같은 동작을 연결할 수 있다
- 🔢 일반 변수는 함수 호출/리렌더링마다 초기화되지만, `useRef`는 그 값을 계속 유지한다 - 자동 증가 id처럼 화면에 안 보이는 값에 적합
- 📋 배열은 `map`으로 JSX 배열로 변환해서 렌더링하고, 각 항목엔 고유한 `key`가 필요하다
- ☑️ 반복문 안 특정 항목 식별은 클로저로 직접 넘기거나, DOM 속성에 심어서 `e.target`으로 읽는 두 가지 방법이 있다
- ⚠️ `[...배열]`은 배열만 복사하고 안의 객체는 원본과 공유한다 - 진짜 불변성을 지키려면 객체도 새로 만들어야 한다
