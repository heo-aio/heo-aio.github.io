## 📦 정적 할당과 동적 할당

```c
int global_var = 10;              // 정적 할당 - Data 영역
int* ptr = malloc(sizeof(int));   // 동적 할당 - Heap 영역
```

지난 글의 메모리 구조와 바로 이어지는 내용이었다. **정적 할당**은 실행되기 전에 이미 크기와 위치가 정해지는 방식(Data 영역), **동적 할당**은 실행 중 필요한 시점에 크기를 정해서 확보하는 방식(Heap 영역)이다. 둘 다 "메모리를 쓴다"는 결과는 같은데, **"언제 그 크기를 결정하는가"**가 진짜 차이라는 걸 다시 짚었다. 그래서 동적 할당은 유연한 대신, 다 쓰고 나면 직접(또는 GC로) 해제해야 하는 책임이 따라온다 - 안 하면 지난 글에서 다룬 메모리 누수로 이어진다.

> ✅ **핵심**: 정적/동적 할당의 차이는 "메모리 크기를 언제 결정하는가"다. 정적은 실행 전, 동적은 실행 중.

## 🔄 프로세스의 5가지 상태

프로세스는 생성부터 종료까지 한 번에 쭉 실행되는 게 아니라, 여러 상태를 오가면서 실행된다. 지난 글에서 짚었던 PCB의 "상태" 필드가 바로 이 값을 담고 있는 것이다.

![프로세스 상태 전이도 - 각 화살표가 어떤 사건으로 일어나는지](/images/os/process_state_diagram.svg)

| 상태 | 의미 | 무엇을 기다리는가 |
|---|---|---|
| New | 프로세스 생성 중 | 메모리 확보 |
| Ready | 실행 준비 완료 | CPU 배정 |
| Running | CPU 점유 중, 실제 실행 | - |
| Waiting | I/O나 이벤트 대기 | 특정 이벤트(파일 읽기 완료 등) |
| Terminated | 실행 종료 | - |

**웹 브라우저로 파일을 다운로드하는 상황**으로 그려보면 흐름이 명확해진다: 브라우저가 실행되어 `Ready`에서 기다리다가, CPU를 받아 `Running`으로 다운로드를 시작한다. 다운로드는 디스크/네트워크 I/O라서 `Waiting`으로 전환되고, 다운로드가 끝나면 다시 `Ready`로 돌아와 CPU를 재할당받아 `Running`으로 마무리한다.

여기서 처음엔 `Ready`와 `Waiting`이 "둘 다 실행 안 되고 있는 상태"라 비슷해 보였는데, 다이어그램으로 그려보고 나서 **"무엇을 기다리는가"**가 다르다는 게 명확해졌다. `Ready`는 오직 CPU 하나만 기다리는 상태라 스케줄러가 마음만 먹으면 바로 `Running`으로 보낼 수 있지만, `Waiting`은 디스크나 네트워크처럼 **CPU가 아무리 줘도 소용없는** 외부 이벤트를 기다리는 상태다. 그래서 `Waiting`에서 나오려면 반드시 그 이벤트(I/O 완료)가 먼저 일어나야 하고, 나온 다음에도 곧바로 `Running`이 아니라 **한 번 더 `Ready`를 거쳐야** CPU를 다시 배정받는다는 것도 이번에 정확히 짚었다.

> ✅ **핵심**: `Ready`는 CPU만 기다리는 상태, `Waiting`은 CPU와 무관한 외부 이벤트를 기다리는 상태다. `Waiting`에서 나와도 곧바로 실행되는 게 아니라 `Ready`를 거쳐야 한다.

## 🔗 멀티 프로세스와 IPC

여러 프로세스(브라우저, 메신저, 음악 플레이어 등)를 동시에 실행하는 걸 멀티 프로세스 환경이라고 한다. 그런데 지난 글에서 봤듯 **프로세스는 각자 독립된 메모리 공간**을 쓴다 - 그래서 "여러 개 떠 있으면 알아서 데이터를 공유하지 않을까" 생각했던 게 틀렸다는 걸 알았다. 독립적이기 때문에 오히려 데이터를 주고받으려면 **IPC(Inter Process Communication)**라는 별도의 통신 방식이 필요하다.

| 방식 | 설명 | 특징 |
|---|---|---|
| Message Queue | 메시지를 큐에 넣고 꺼내는 방식 | 커널이 중계, 비교적 간단 |
| Shared Memory | 메모리의 일부를 공유 영역으로 매핑 | 가장 빠름, 대신 동기화를 직접 처리해야 함 |
| Socket | 네트워크 프로토콜 기반 통신 | 같은 컴퓨터든 다른 컴퓨터든 동일하게 사용 가능 |

웹 서버와 데이터베이스 서버가 보통 **별도의 프로세스**로 떠 있고 `Socket`으로 데이터를 주고받는다는 예시를 보면서, "왜 굳이 Shared Memory처럼 빠른 방법을 안 쓰지?"라는 의문이 들었다. 생각해보니 웹 서버와 DB 서버는 아예 다른 컴퓨터(서버)에 있을 수도 있는 관계라서, **같은 메모리를 공유한다는 전제 자체가 불가능**한 경우가 많다. 반면 `Shared Memory`는 물리적으로 같은 메모리에 접근 가능한 프로세스끼리(같은 컴퓨터 안에서)만 쓸 수 있는 방식이라, "얼마나 빠른가"보다 "애초에 그 방식이 가능한 상황인가"를 먼저 따져야 한다는 걸 알았다.

> ✅ **핵심**: 프로세스는 독립된 메모리를 쓰기 때문에 IPC가 필요하다. 어떤 IPC를 쓸지는 속도뿐 아니라 "프로세스들이 물리적으로 메모리를 공유할 수 있는 위치에 있는가"로도 결정된다.

## ⚙️ CPU 스케줄링 - 직접 계산해서 비교하기

CPU는 한 번에 하나의 작업만 처리하는데, 여러 프로그램이 동시에 도는 것처럼 보이는 이유는 운영체제가 **누구에게 얼마나 CPU를 줄지**를 계속 결정하기 때문이다(CPU 스케줄링). 이번엔 이걸 그냥 "장단점 표"로 외우지 않고, 같은 프로세스 세트로 세 방식을 직접 계산해봤다.

**조건**: P1=5, P2=3, P3=8, P4=6 (버스트 타임, 전부 t=0에 도착), Round Robin의 Time Quantum=4

![FCFS, SJF, RR을 같은 프로세스로 직접 계산한 간트 차트와 평균 대기시간 비교](/images/os/scheduling_gantt.svg)

- **FCFS (First Come First Served)**: 도착 순서대로 처리. 구현은 제일 단순하지만, 앞에 긴 작업(P3=8)이 있으면 뒤 작업들이 전부 밀리는 **Convoy Effect**가 그대로 계산에서 드러났다. 평균 대기시간 **7.25**.
- **SJF (Shortest Job First)**: 짧은 작업부터 처리. 평균 대기시간이 **6.25**로 셋 중 가장 낮았다 - "평균 대기시간을 최소화한다"는 설명이 계산으로도 확인됐다.
- **RR (Round Robin, Quantum=4)**: 일정 시간마다 돌아가며 실행. 그런데 평균 대기시간이 **10.75**로 오히려 셋 중 제일 나빴다.

세 번째 결과가 예상 밖이었다. "Round Robin은 공정하고 응답성이 좋다"고만 외웠는데 막상 계산해보니 **평균 대기시간은 가장 나쁘게** 나온 것이다. 왜 그런지 다시 생각해보니, Round Robin이 잘하는 건 "평균 대기시간"이 아니라 **"첫 응답까지 걸리는 시간(response time)"**이었다. 모든 프로세스가 최대 Quantum(4) 안에는 한 번씩 실행 기회를 얻기 때문에 "화면이 멈춘 것처럼 보이는 시간"은 짧아지지만, 작업을 여러 번 나눠서 돌아가며 처리하다 보니 각 작업이 완전히 끝나기까지의 시간(그리고 그 과정에서의 대기시간 총합)은 오히려 늘어날 수 있다. 그래서 Round Robin이 "대화형(interactive) 시스템에 적합하다"고 배우는 이유가, 대기시간이 짧아서가 아니라 **응답성이 좋아서**였다는 걸 계산을 해보고서야 정확히 이해했다.

> ✅ **핵심**: FCFS는 단순하지만 Convoy Effect가 있고, SJF는 평균 대기시간이 가장 짧지만 짧은 작업이 계속 들어오면 긴 작업이 밀릴 수 있다(기아 상태의 씨앗). RR은 평균 대기시간보다 "응답성"이 강점이라 대화형 시스템에 적합하다.

## 🚨 Deadlock과 Starvation

둘 다 "프로세스가 실행되지 못하는 상황"이라 처음엔 같은 개념인 줄 알았는데, 원인이 다르다.

![Deadlock - 두 프로세스가 서로의 자원을 기다리며 순환대기에 빠지는 상황](/images/os/deadlock_conditions.svg)

**Deadlock**은 프로세스들이 서로가 가진 자원을 기다리며 전부 멈춰버리는 상황이다. 이게 성립하려면 아래 4가지 조건이 **동시에** 필요하다:

1. **상호배제** - 자원을 한 프로세스만 독점해서 쓸 수 있음
2. **점유대기** - 자원을 쥔 채로 다른 자원을 추가로 요청함
3. **비선점** - 그 자원을 강제로 빼앗을 수 없음
4. **순환대기** - 요청이 원을 그리며 서로를 기다림 (P1→R2 요청, P2→R1 요청)

넷 다 필요하다는 게 처음엔 "그냥 이유 없이 외워야 하는 조건 목록"처럼 느껴졌는데, 다이어그램을 그려보고 나니 **"넷 중 하나만 깨져도 순환이 끊긴다"**는 걸 알 수 있었다. 예를 들어 ③번(비선점)이 없다면 - 즉 자원을 강제로 뺏을 수 있다면 - P1이 요청을 무한정 기다릴 필요 없이 운영체제가 P2의 R2를 뺏어서 P1에게 줄 수 있으니 애초에 순환이 안 생긴다. 이 관점으로 보니 Deadlock을 막는 방법(Deadlock Prevention)이 왜 "이 4가지 조건 중 하나를 깨는 정책을 세우는 것"으로 설명되는지 이해가 됐다.

**Starvation**은 이것과 달리, 특정 프로세스가 계속 자원(또는 CPU)을 할당받지 못하는 상황이다. 예를 들어 위에서 본 SJF 스케줄링에서, 짧은 작업이 계속 새로 들어오면 긴 작업은 우선순위에서 영원히 밀릴 수 있다 - 이게 Starvation이다. 해결책으로는 **Aging**(오래 기다린 프로세스의 우선순위를 점점 높여주는 방식)이 있다고 하는데, "SJF의 평균 대기시간이 낮다고 무조건 좋은 게 아니구나"를 스케줄링 계산 파트와 자연스럽게 연결해서 이해할 수 있었다.

> ✅ **핵심**: Deadlock은 4가지 조건이 동시에 성립할 때 발생하고, 하나만 깨도 방지할 수 있다. Starvation은 자원 배분이 한쪽으로 계속 쏠려서 생기며, Aging으로 완화할 수 있다.

## 🤔 감이 안 왔던 부분, 다시 짚어보기

- **Waiting에서 Ready로 돌아온 다음, 왜 곧바로 Running이 아닌가?** → 처음엔 "I/O가 끝났으면 바로 실행되는 거 아닌가" 싶었는데, 그 순간에도 CPU는 다른 프로세스가 쓰고 있을 수 있다. `Waiting → Ready`는 "이제 실행할 준비가 됐다"는 뜻일 뿐, "지금 당장 CPU를 준다"는 뜻이 아니다. CPU를 실제로 받는 건 스케줄러가 다시 `dispatch`를 결정하는 순간이라는 걸 상태 다이어그램을 그려보고 나서야 명확해졌다.
- **RR의 Quantum은 어떻게 정하나?** → 이번 계산에서 Quantum=4가 오히려 대기시간을 늘리는 걸 봤는데, 그럼 Quantum을 마냥 키우면 되는 걸까 싶었다. 하지만 Quantum을 무한히 키우면 사실상 FCFS와 같아지고, 너무 작게 잡으면 문맥 전환(context switching) 비용이 커진다고 한다. 다음엔 Quantum 값을 여러 개(1, 2, 8 등)로 바꿔가며 같은 프로세스 세트로 평균 대기시간이 어떻게 변하는지 직접 계산해서 "적당한 값"의 감을 잡아봐야겠다.
- **Deadlock 4가지 조건을 다 깨는 게 항상 좋은 걸까?** → 예를 들어 상호배제를 깨서 여러 프로세스가 자원을 동시에 쓰게 하면 Deadlock은 안 생기겠지만, 프린터 같은 자원은애초에 동시에 쓰면 안 되는(상호배제가 필요한) 경우도 있다. 그래서 실제로는 조건을 깨는 대신 **Deadlock Avoidance**(안전 상태를 유지하며 자원을 배분)나 **Deadlock Detection**(발생을 감지하고 사후 처리)처럼 다른 전략도 쓴다고 하니, 이 부분은 다음에 따로 정리해봐야겠다.

## 💡 정리하면

이번 글에서 제일 값졌던 건 스케줄링을 "장단점 암기"가 아니라 **직접 계산**해서 확인한 부분이었다. "RR은 응답성이 좋다"는 문장을 외우는 것과, 실제로 평균 대기시간이 SJF보다 나쁘게 나오는 걸 숫자로 확인하고 그 이유(응답시간 vs 대기시간은 다른 지표)를 스스로 짚어내는 건 완전히 다른 이해의 깊이였다. Deadlock의 4가지 조건도 마찬가지로, 그냥 나열이 아니라 "하나만 깨도 막을 수 있다"는 관점으로 보니 왜 그 조건들이 함께 제시되는지 이해가 됐다.

**오늘의 핵심 6가지**

- 📦 정적/동적 할당의 차이는 "메모리 크기를 언제 정하는가"다
- 🔄 `Ready`는 CPU만, `Waiting`은 외부 이벤트를 기다리며, `Waiting`에서 나와도 `Ready`를 거쳐야 실행된다
- 🔗 프로세스는 독립된 메모리를 쓰기 때문에 IPC가 필요하고, 어떤 방식을 쓸지는 속도뿐 아니라 물리적 위치 관계로도 결정된다
- ⚙️ FCFS는 단순하지만 Convoy Effect, SJF는 평균 대기시간 최소지만 Starvation 위험, RR은 대기시간보다 응답성이 강점이다
- 🚨 Deadlock은 4조건 동시 성립이 필요하고 하나만 깨도 막을 수 있다
- 🕳️ Starvation은 자원 배분 쏠림 문제이며 Aging으로 완화한다
